Lesson 37 — Events in C#

Module 2.2 — Advanced Language Features

1. What Is an Event?

An event is a C# mechanism used for communication between objects, especially when one object needs to notify other objects that something has happened.

The basic idea is:

Something happens
      ↓
Publisher raises event
      ↓
Subscribers are notified
      ↓
Their methods execute

For example:

Payment completed
      ↓
Payment event raised
      ↓
Email subscriber → sends email
SMS subscriber   → sends SMS
Logging subscriber → writes log

Events are built on top of delegates.

You already learned:

A delegate represents callable behavior.

An event adds an important restriction:

Subscribers can subscribe/unsubscribe, but normally only the class that owns the event can raise it.

That distinction is one of the most important things to understand.

2. Why Do We Need Events?

Suppose we have a Button:

class Button
{
    public void Click()
    {
        Console.WriteLine("Button clicked");
    }
}

What if other parts of the application need to know when the button is clicked?

For example:

Button clicked
     ↓
 ┌───┼──────────────┐
 ↓   ↓              ↓
UI  Logger       Analytics

The button should not need to directly know about all these components.

Instead, it can announce:

"I was clicked."

Other objects can subscribe.

This creates loose communication between objects.

3. Publisher and Subscriber

Events commonly involve two roles.

Publisher

The object that owns and raises the event.

Example:

class Button
{
    // event belongs to Button
}
Subscriber

The object that wants to receive notification.

Example:

class Logger
{
    // subscribes to Button event
}

Mental model:

             Publisher
                |
             Event
                |
       ┌────────┼────────┐
       ↓        ↓        ↓
 Subscriber  Subscriber  Subscriber

The publisher does not need to know exactly what each subscriber does.

4. Events Are Built on Delegates

Suppose you already have:

delegate void MessageHandler();

You could create:

MessageHandler handler;

and add methods:

handler += Method1;
handler += Method2;

An event uses similar underlying mechanics:

event MessageHandler SomethingHappened;

So:

Delegate
   ↓
provides callable method references

Event
   ↓
provides controlled publish/subscribe behavior
5. Basic Event Syntax

Example:

class Button
{
    public event Action Clicked;
}

This declares an event named:

Clicked

using:

Action

as its delegate type.

A subscriber can do:

button.Clicked += OnButtonClicked;

and unsubscribe:

button.Clicked -= OnButtonClicked;

But the important part comes next.

6. Raising an Event

The class that owns the event can raise it:

class Button
{
    public event Action Clicked;

    public void Click()
    {
        Clicked?.Invoke();
    }
}

Now:

Button button = new Button();

button.Clicked += OnButtonClicked;

button.Click();

Subscriber:

static void OnButtonClicked()
{
    Console.WriteLine("Button was clicked!");
}

Output:

Button was clicked!

The flow is:

button.Click()
      ↓
Clicked?.Invoke()
      ↓
OnButtonClicked()
7. Why ?.Invoke()?

This:

Clicked?.Invoke();

means:

Invoke the event only if at least one subscriber exists.

Without the null check:

Clicked.Invoke();

if nobody has subscribed, the event may be null.

That could result in:

NullReferenceException

The null-conditional operator prevents that.

8. Complete Basic Example
using System;

class Button
{
    public event Action Clicked;

    public void Click()
    {
        Console.WriteLine("Button clicked.");

        Clicked?.Invoke();
    }
}

class Program
{
    static void OnButtonClicked()
    {
        Console.WriteLine("Subscriber received notification.");
    }

    static void Main()
    {
        Button button = new Button();

        button.Clicked += OnButtonClicked;

        button.Click();
    }
}

Output:

Button clicked.
Subscriber received notification.
9. What Does += Mean for Events?

When you write:

button.Clicked += OnButtonClicked;

you are saying:

"Subscribe OnButtonClicked to this event."

Conceptually:

Clicked event
     |
     +── OnButtonClicked

If another subscriber joins:

button.Clicked += SendEmail;

then:

Clicked event
     |
     +── OnButtonClicked
     |
     +── SendEmail

When the event is raised:

Clicked?.Invoke();

both subscribers are invoked.

10. Multiple Subscribers
class Program
{
    static void LogClick()
    {
        Console.WriteLine("Logging click.");
    }

    static void SendNotification()
    {
        Console.WriteLine("Sending notification.");
    }

    static void Main()
    {
        Button button = new Button();

        button.Clicked += LogClick;
        button.Clicked += SendNotification;

        button.Click();
    }
}

Output:

Button clicked.
Logging click.
Sending notification.

The publisher does not need:

LogClick();
SendNotification();

It only raises:

Clicked?.Invoke();

The event system handles the subscribers.

11. Unsubscribing

You subscribe using:

+=

You unsubscribe using:

-=

Example:

button.Clicked += LogClick;
button.Clicked += SendNotification;

button.Clicked -= LogClick;

Now only:

SendNotification

remains subscribed.

This is important because subscribers may have a lifetime shorter than the publisher.

12. Why Events Are Safer Than Public Delegates

This is a critical concept.

Suppose we expose a delegate directly:

public Action Clicked;

External code can potentially do:

button.Clicked = SomeMethod;

or:

button.Clicked?.Invoke();

That means external code has too much control.

With an event:

public event Action Clicked;

external code can normally:

button.Clicked += SomeMethod;
button.Clicked -= SomeMethod;

but cannot normally raise the event:

button.Clicked?.Invoke(); // Not allowed outside Button

The publisher controls when the event occurs.

This is the major conceptual difference:

Public delegate
    ↓
External code can replace/invoke it

Event
    ↓
External code subscribes/unsubscribes
Publisher controls invocation
13. The Core Event Rule

Remember:

Subscribers control subscription. Publisher controls invocation.

This is the heart of C# events.

Subscriber
    |
    +── +=
    |
    +── -=

Publisher
    |
    +── Invoke / raise
14. Event Declaration

You can declare an event using a custom delegate:

delegate void NotifyHandler();

class Process
{
    public event NotifyHandler Completed;
}

Or using a built-in delegate:

class Process
{
    public event Action Completed;
}

Both are possible.

Modern C# commonly uses built-in delegate types such as Action or the standard EventHandler pattern.

15. EventHandler

.NET provides a standard delegate specifically for events:

EventHandler

Its basic signature is:

void Handler(object? sender, EventArgs e)

Example:

class Button
{
    public event EventHandler Clicked;

    public void Click()
    {
        Clicked?.Invoke(this, EventArgs.Empty);
    }
}

Subscriber:

static void OnClicked(object? sender, EventArgs e)
{
    Console.WriteLine("Button clicked.");
}

Subscription:

button.Clicked += OnClicked;
16. Why sender?

The sender parameter identifies the object that raised the event.

Example:

Clicked?.Invoke(this, EventArgs.Empty);

Here:

this
 ↓
Button object

The subscriber can therefore know which object generated the event.

For example:

static void OnClicked(object? sender, EventArgs e)
{
    Button button = (Button)sender;

    Console.WriteLine("Event came from a Button.");
}

However, modern code often avoids unnecessary casts when the event source is already known.

17. Why EventArgs?

EventArgs represents event-related data.

For an event with no additional information:

EventArgs.Empty

is used.

Example:

Clicked?.Invoke(this, EventArgs.Empty);

The event communicates:

Who raised it?
    ↓
this

Additional data?
    ↓
None
18. Events With Custom Data

Suppose an order is completed and subscribers need to know:

order ID
amount
completion time

A simple EventArgs is not enough.

We can create custom event data.

class OrderCompletedEventArgs : EventArgs
{
    public int OrderId { get; }
    public decimal Amount { get; }

    public OrderCompletedEventArgs(
        int orderId,
        decimal amount)
    {
        OrderId = orderId;
        Amount = amount;
    }
}

Then:

class OrderService
{
    public event EventHandler<OrderCompletedEventArgs> OrderCompleted;

    public void CompleteOrder(
        int orderId,
        decimal amount)
    {
        Console.WriteLine("Order completed.");

        var args = new OrderCompletedEventArgs(
            orderId,
            amount);

        OrderCompleted?.Invoke(this, args);
    }
}

Subscriber:

static void OnOrderCompleted(
    object? sender,
    OrderCompletedEventArgs e)
{
    Console.WriteLine(
        $"Order {e.OrderId} completed for {e.Amount}.");
}

Usage:

OrderService service = new OrderService();

service.OrderCompleted += OnOrderCompleted;

service.CompleteOrder(101, 500);

Output:

Order completed.
Order 101 completed for 500.
19. EventHandler<TEventArgs>

This is the standard pattern for events carrying custom data:

EventHandler<TEventArgs>

where TEventArgs derives from:

EventArgs

Example:

public event EventHandler<OrderCompletedEventArgs> OrderCompleted;

Conceptually:

EventHandler<TEventArgs>
        |
        +── sender
        |
        +── event data

This standardizes event communication across .NET applications.

20. Event Naming Convention

Events are usually named using something that describes what happened.

Good:

Clicked
Completed
Started
Stopped
Cancelled
OrderCreated
PaymentCompleted

Avoid vague names like:

DoSomething
Event1
Handler
Thing

A useful naming pattern is:

SomethingHappened

Examples:

OrderCreated
PaymentCompleted
FileDownloaded
ConnectionClosed
21. Event Handler Naming Convention

Methods handling events commonly use:

On + EventName

Examples:

OnClicked
OnOrderCompleted
OnPaymentCompleted
OnFileDownloaded

Example:

static void OnOrderCompleted(
    object? sender,
    OrderCompletedEventArgs e)
{
}

This is a convention, not a compiler requirement.

22. Full Standard Event Pattern

A typical implementation looks like this:

using System;

class OrderCompletedEventArgs : EventArgs
{
    public int OrderId { get; }

    public OrderCompletedEventArgs(int orderId)
    {
        OrderId = orderId;
    }
}

class OrderService
{
    public event EventHandler<OrderCompletedEventArgs> OrderCompleted;

    public void CompleteOrder(int orderId)
    {
        Console.WriteLine("Completing order...");

        OrderCompleted?.Invoke(
            this,
            new OrderCompletedEventArgs(orderId));
    }
}

class Program
{
    static void Main()
    {
        OrderService service = new OrderService();

        service.OrderCompleted += OnOrderCompleted;

        service.CompleteOrder(101);
    }

    static void OnOrderCompleted(
        object? sender,
        OrderCompletedEventArgs e)
    {
        Console.WriteLine(
            $"Order {e.OrderId} completed.");
    }
}

The architecture is:

                OrderService
                     |
              OrderCompleted
                     |
        ┌────────────┼────────────┐
        ↓            ↓            ↓
      Email         Logger       Analytics
23. Why This Creates Loose Coupling

Imagine this without events:

class OrderService
{
    EmailService email;
    SmsService sms;
    Logger logger;

    public void CompleteOrder()
    {
        email.Send();
        sms.Send();
        logger.Log();
    }
}

OrderService now knows about all those components.

With events:

class OrderService
{
    public event EventHandler OrderCompleted;

    public void CompleteOrder()
    {
        OrderCompleted?.Invoke(
            this,
            EventArgs.Empty);
    }
}

Now OrderService only knows:

"An order has completed."

It doesn't need to know who is listening.

That is a major architectural benefit.

24. Events and Loose Coupling

Without event:

OrderService
    |
    +── EmailService
    |
    +── SmsService
    |
    +── Logger

Strong knowledge of dependencies.

With event:

                 Event
                   ↑
                   |
             OrderService
                   |
        ┌──────────┼──────────┐
        ↓          ↓          ↓
      Email       SMS       Logger

The publisher and subscribers communicate through the event contract.

25. Event Lifecycle

A typical event has this lifecycle:

1. Event declared
       ↓
2. Subscriber subscribes
       ↓
3. Something happens
       ↓
4. Publisher raises event
       ↓
5. Event invokes subscribers
       ↓
6. Subscriber handles event
       ↓
7. Subscriber may unsubscribe

Example:

service.OrderCompleted += OnOrderCompleted;

↓

service.CompleteOrder();

↓

OrderCompleted?.Invoke(...);

↓

OnOrderCompleted(...);

↓

service.OrderCompleted -= OnOrderCompleted;
26. Event Is Not the Same as a Delegate

They are closely related, but they are not the same thing.

Delegate
Action action;

Represents a callable method reference.

Event
event Action SomethingHappened;

Provides controlled publish/subscribe semantics around delegate-based invocation.

Think:

Delegate
    ↓
"Here is callable behavior."

Event
    ↓
"Subscribe to this notification."
27. Event vs Callback

These concepts are related but different.

Callback

Usually:

One operation
    ↓
calls supplied method

Example:

ProcessData(callback);
Event

Usually:

One publisher
    ↓
notifies
    ↓
zero or many subscribers

Example:

OrderCompleted

So:

Callback → often one supplied behavior

Event → notification mechanism with subscribers
28. Events Can Have Zero Subscribers

This is completely valid:

OrderCompleted?.Invoke(
    this,
    EventArgs.Empty);

If nobody subscribed:

Subscribers = 0

nothing happens.

That is one reason event invocation commonly uses:

?.Invoke()
29. Event Subscription Is a Runtime Relationship

Consider:

button.Clicked += OnClicked;

This does not permanently modify the Button class.

It creates a runtime relationship:

Button instance
      |
      +── Clicked
             |
             +── OnClicked

Another button can have different subscribers:

Button A
   ↓
OnButtonAClicked

Button B
   ↓
OnButtonBClicked

The event subscription belongs to the object instance.

30. Important Memory Consideration

Events can create an important lifetime issue.

Suppose:

Long-lived Publisher
        |
        ↓
event
        |
        ↓
Short-lived Subscriber

If the subscriber remains subscribed, the publisher may retain a reference to it through the event subscription.

This can prevent the subscriber from becoming eligible for garbage collection as expected.

Therefore, when subscription lifetime matters, unsubscribe:

publisher.Event -= handler;

This is especially important with long-lived publishers such as:

application-wide services
static events
UI/global event sources
long-running processes

The exact lifetime behavior depends on the objects and references involved, but the general rule is:

Manage event subscriptions according to object lifetime.

31. Events and Encapsulation

Events are strongly connected to encapsulation.

Consider:

public event EventHandler Completed;

External code gets limited access:

service.Completed += Handler;
service.Completed -= Handler;

but cannot normally do:

service.Completed?.Invoke(...);

The publisher retains control over the event.

So events combine:

Delegate
   +
Encapsulation
   +
Publish/Subscribe
32. Common Mistakes
Mistake 1 — Trying to raise an event externally
service.Completed?.Invoke(
    service,
    EventArgs.Empty);

from outside the declaring type is not allowed for a normal event.

The publisher should raise it.

Mistake 2 — Forgetting to unsubscribe

Repeated subscription:

button.Clicked += OnClicked;
button.Clicked += OnClicked;

can result in the handler being invoked multiple times.

Be careful about repeated subscriptions.

Mistake 3 — Using = instead of +=

For subscription:

button.Clicked += OnClicked;

not:

button.Clicked = OnClicked;

An event is not meant to be externally replaced like a delegate variable.

Mistake 4 — Confusing event declaration with event invocation

Declaration:

public event EventHandler Completed;

Invocation:

Completed?.Invoke(this, EventArgs.Empty);

They serve completely different purposes.

33. Event vs Delegate — Final Comparison
Feature	Delegate	Event
Represents method reference	Yes	Uses delegate internally
Can invoke directly	Yes	Only declaring type normally raises it
+= supported	Yes	Yes
-= supported	Yes	Yes
Multiple methods	Yes	Yes
Publish/subscribe semantics	No	Yes
External code can normally raise it	Yes for exposed delegate	No
Main purpose	Pass behavior	Notify subscribers

The most important difference:

Delegate
    ↓
Callable behavior

Event
    ↓
Controlled notification
34. Deep Mental Model

Imagine a YouTube channel.

YouTube Channel
      ↓
Publisher
      ↓
"New video uploaded!"
      ↓
Event
      ↓
Subscribers
 ┌────┼────┐
 ↓    ↓    ↓
A     B    C

The channel doesn't manually call:

A.Notify()
B.Notify()

It raises the notification.

The subscription system determines who receives it.

C# events provide this programming model.
