Generics & Generic Constraints

Module 2.2 — Advanced Language Features

You have already used:

List<int>
List<string>
Dictionary<int, string>

So you have already been using generics.

Now we go deeper into how generics work, why they exist, and how to create your own generic types and methods.

1. What Is a Generic?

A generic allows you to write code using a type parameter instead of committing to one specific type.

For example:

List<int>

and:

List<string>

use the same generic type:

List<T>

where:

T
↓
type parameter

So:

List<T>
   ↓
   T = int
   ↓
List<int>

and:

List<T>
   ↓
   T = string
   ↓
List<string>

The important idea:

Write the logic once, allow the caller to specify the type.

2. Why Do We Need Generics?

Imagine you want a method that returns the first element of an array.

Without generics, you might write:

static int GetFirst(int[] values)
{
    return values[0];
}

Then for strings:

static string GetFirst(string[] values)
{
    return values[0];
}

Then for double:

static double GetFirst(double[] values)
{
    return values[0];
}

The logic is identical.

Only the type changes.

Generics solve this:

static T GetFirst<T>(T[] values)
{
    return values[0];
}

Now one method works with many types.

3. The Generic Type Parameter

Look at:

static T GetFirst<T>(T[] values)
{
    return values[0];
}

There are two important Ts.

T
↓
return type

<T>
 ↓
type parameter declaration

And:

T[] values

means the parameter is an array of the same generic type.

So:

GetFirst<T>
      ↓
      T
      ↓
type selected by caller
4. Calling a Generic Method

Given:

static T GetFirst<T>(T[] values)
{
    return values[0];
}

You can call:

int[] numbers = { 10, 20, 30 };

int first = GetFirst<int>(numbers);

Here:

T = int

So conceptually the compiler sees:

GetFirst<int>

For strings:

string[] names =
{
    "Alice",
    "Bob"
};

string firstName =
    GetFirst<string>(names);

Here:

T = string
5. Type Inference

You often don't need to explicitly write:

GetFirst<int>(numbers);

The compiler can infer T from the argument:

GetFirst(numbers);

Because:

int[] numbers

matches:

T[] values

therefore:

T = int

So both are valid:

GetFirst<int>(numbers);

and:

GetFirst(numbers);

The second is usually cleaner.

6. Generic Method Syntax

The general syntax is:

returnType MethodName<T>(parameters)
{
}

Example:

static T Identity<T>(T value)
{
    return value;
}

Call:

int number = Identity(10);

string text = Identity("Hello");

The same method works with both.

7. Generic Method With Two Type Parameters

A method can have multiple type parameters.

static void PrintPair<T1, T2>(
    T1 first,
    T2 second)
{
    Console.WriteLine(first);
    Console.WriteLine(second);
}

Usage:

PrintPair(10, "Hello");

The compiler infers:

T1 = int
T2 = string

Another call:

PrintPair("Age", 25);

Now:

T1 = string
T2 = int

So type parameters can represent different types independently.

8. Generic Class

Generics are not limited to methods.

You can create generic classes.

class Box<T>
{
    private T value;

    public Box(T value)
    {
        this.value = value;
    }

    public T GetValue()
    {
        return value;
    }
}

Now:

Box<int> numberBox =
    new Box<int>(100);

and:

Box<string> textBox =
    new Box<string>("Hello");

Conceptually:

Box<T>
   |
   +── T = int
   |      ↓
   |   Box<int>
   |
   +── T = string
          ↓
       Box<string>
9. Generic Classes Are Strongly Typed

Consider:

Box<int> box =
    new Box<int>(100);

You cannot put a string into that box:

box = new Box<int>("Hello");

This is a compile-time error.

The generic type preserves type safety.

That's one of the major advantages of generics.

10. Generic vs object

Before generics, developers often used object to make code work with multiple types.

Example:

class Box
{
    private object value;

    public Box(object value)
    {
        this.value = value;
    }

    public object GetValue()
    {
        return value;
    }
}

Now:

Box box = new Box(100);

object value = box.GetValue();

int number = (int)value;

Notice the cast.

With generics:

class Box<T>
{
    private T value;

    public Box(T value)
    {
        this.value = value;
    }

    public T GetValue()
    {
        return value;
    }
}

Then:

Box<int> box =
    new Box<int>(100);

int number = box.GetValue();

No cast is required.

11. Why Generics Are Better Than object

Compare:

object
  ↓
less type information
  ↓
casting often required
  ↓
runtime errors possible

with:

generic
  ↓
type known at compile time
  ↓
no unnecessary casting
  ↓
better type safety

Generics also allow the runtime to work efficiently with value types without forcing the same boxing pattern that an object-based design would.

12. Generic Collections

You already used:

List<int>

This is:

List<T>

where:

T = int

Similarly:

List<string>

means:

T = string

And:

Dictionary<int, string>

has two type parameters:

TKey    = int
TValue  = string

This is the same generic system you are now learning to build yourself.

13. Generic Interfaces

You can create generic interfaces:

interface IRepository<T>
{
    void Add(T item);

    T Get(int id);
}

Then:

class UserRepository
    : IRepository<User>
{
    public void Add(User user)
    {
    }

    public User Get(int id)
    {
        return new User();
    }
}

The interface becomes specialized for:

T = User

Another class could use:

IRepository<Product>

So the same abstraction can work with different types.

14. Generic Type Parameters Have No Assumptions

This is an important limitation.

Suppose:

static T GetLarger<T>(T a, T b)
{
    // Which one is larger?
}

You might try:

if (a > b)

But this does not generally compile.

Why?

Because T could be:

int
string
DateTime
Customer
Product
...

The compiler cannot assume that every possible T supports the > operator.

This leads directly to generic constraints.

15. What Is a Generic Constraint?

A generic constraint tells the compiler:

"T cannot be absolutely anything. T must satisfy this requirement."

Syntax:

where T : ...

Example:

static void PrintName<T>(T value)
    where T : Person
{
    Console.WriteLine(value.Name);
}

Now the compiler knows:

T must be Person
or a derived type of Person

Therefore it can safely access:

value.Name
16. Why Constraints Matter

Without a constraint:

static void Process<T>(T value)
{
}

the compiler has very little information about T.

With:

static void Process<T>(T value)
    where T : Person
{
}

the compiler knows:

T
↓
must be Person or derived from Person

Now members available on Person can be used safely.

17. where T : class

This constraint means:

T must be a reference type.

Example:

static void Process<T>(T value)
    where T : class
{
}

Valid:

Process("Hello");

because string is a reference type.

A custom class is also valid:

class Person
{
}

Process(new Person());

But:

Process(10);

is not valid because int is a value type.

18. where T : struct

This means:

T must be a non-nullable value type.

Example:

static void Process<T>(T value)
    where T : struct
{
}

Valid:

Process(10);
Process(3.14);
Process(true);

because these are value types.

A class is not valid:

class Person
{
}

Process(new Person());

because Person is a reference type.

19. class vs struct Constraint
where T : class
        ↓
reference type

where T : struct
        ↓
value type

Examples:

class
string
arrays
delegates
interfaces

are reference types.

Examples:

int
double
bool
decimal
structs
enums

are value types.

20. where T : new()

This constraint means:

T must have a public parameterless constructor.

Example:

static T Create<T>()
    where T : new()
{
    return new T();
}

Now:

Person person =
    Create<Person>();

provided Person has a public parameterless constructor:

class Person
{
    public Person()
    {
    }
}
21. Why Does new() Matter?

Without the constraint:

static T Create<T>()
{
    return new T();
}

the compiler doesn't know whether T can be constructed with:

new T()

Adding:

where T : new()

guarantees that requirement.

Mental model:

where T : new()
       ↓
T can be created with
new T()
22. Parameterized Constructors and new()

This is important.

Suppose:

class Person
{
    public Person(string name)
    {
    }
}

There is no public parameterless constructor.

Therefore:

static T Create<T>()
    where T : new()
{
    return new T();
}

cannot use:

Create<Person>();

because:

Person
  ↓
no public parameterless constructor
  ↓
fails new() constraint
23. where T : BaseClass

You can constrain T to a base class.

class Animal
{
    public void Eat()
    {
        Console.WriteLine("Eating");
    }
}

Then:

static void Feed<T>(T animal)
    where T : Animal
{
    animal.Eat();
}

Now:

Feed(new Dog());

works if:

class Dog : Animal
{
}

because:

Dog IS-A Animal

But an unrelated class cannot be used.

24. Why Base-Class Constraints Are Useful

Without:

where T : Animal

you cannot safely do:

animal.Eat();

because T might be anything.

With the constraint:

T
↓
Animal or derived class
↓
Eat() guaranteed

This allows generic code to work against a common abstraction.

25. where T : Interface

You can constrain a generic type to an interface.

Example:

interface IPrintable
{
    void Print();
}

Then:

static void PrintItem<T>(T item)
    where T : IPrintable
{
    item.Print();
}

Any type implementing IPrintable can be used.

class Invoice : IPrintable
{
    public void Print()
    {
        Console.WriteLine("Invoice");
    }
}

Then:

PrintItem(new Invoice());

works.

26. Why Interface Constraints Are Powerful

This is one of the most useful generic patterns.

Instead of saying:

T must be this exact class

you say:

T must support this capability

Example:

where T : IPrintable

means:

"I don't care what T actually is.
I only require that T can Print()."

This works naturally with abstraction and polymorphism.

27. Multiple Constraints

A type parameter can have multiple constraints.

Example:

static T CreateAndProcess<T>()
    where T : Person, IPrintable, new()
{
    T item = new T();

    item.Print();

    return item;
}

Here T must satisfy all three:

T
├── Person
├── IPrintable
└── public parameterless constructor

All constraints must be satisfied.

28. Constraint Ordering

A common pattern is:

where T : BaseClass, IInterface, new()

For example:

static T Create<T>()
    where T : Person, IPrintable, new()
{
    return new T();
}

Conceptually:

Base class
    ↓
interfaces
    ↓
new()

The exact legal combinations follow C#'s generic constraint rules, so don't treat the order as merely stylistic when combining special constraints.

29. Multiple Interfaces

A generic type can require multiple interfaces:

static void Process<T>(T item)
    where T : IPrintable, IDisposable
{
    item.Print();
    item.Dispose();
}

Now T must implement both:

IPrintable
+
IDisposable

This lets generic code safely use members from both interfaces.

30. Generic Constraint Hierarchy

The main constraints you should know are:

where T : class
where T : struct
where T : new()
where T : BaseClass
where T : Interface
where T : Interface1, Interface2
where T : BaseClass, Interface1, new()

Each constraint tells the compiler something about T.

31. Constraint = Compile-Time Guarantee

Consider:

static void Print<T>(T value)
    where T : IPrintable
{
    value.Print();
}

The compiler can guarantee:

T implements IPrintable

Therefore:

value.Print();

is legal.

This is a key generic principle:

Constraints provide compile-time guarantees about the capabilities of a type parameter.

32. Generic Method With Interface Constraint

Let's build a realistic example.

interface IEntity
{
    int Id { get; }
}

Generic method:

static void PrintId<T>(T entity)
    where T : IEntity
{
    Console.WriteLine(entity.Id);
}

Now:

class User : IEntity
{
    public int Id { get; set; }
}

Usage:

User user = new User
{
    Id = 101
};

PrintId(user);

The generic method does not care that the object is specifically a User.

It only requires:

IEntity
   ↓
Id
33. Generic Constraints and Polymorphism

This connects directly to your previous lessons.

You learned:

Inheritance
Abstraction
Interfaces
Polymorphism

Now generics can use those concepts as constraints.

Example:

static void Process<T>(T payment)
    where T : IPayment
{
    payment.Pay();
}

The generic method supports any payment type implementing:

IPayment

So:

Generic
   +
Interface constraint
   +
Polymorphism

work together.

34. Generic Class With Constraint

Constraints can also be placed on generic classes.

class Repository<T>
    where T : IEntity
{
    public void Save(T entity)
    {
        Console.WriteLine(entity.Id);
    }
}

Now:

Repository<User> users =
    new Repository<User>();

works if User : IEntity.

But:

Repository<string> repository;

would fail because string doesn't satisfy IEntity.

35. Generic Interface With Constraint

You can also constrain interfaces:

interface IRepository<T>
    where T : IEntity
{
    void Save(T entity);
}

Implementation:

class UserRepository
    : IRepository<User>
{
    public void Save(User user)
    {
        Console.WriteLine(user.Id);
    }
}

This gives you strong compile-time contracts across the entire design.

36. Generic Method vs Generic Class

These are different.

Generic method
class Utility
{
    public static T Identity<T>(T value)
    {
        return value;
    }
}

Only the method is generic.

Generic class
class Box<T>
{
    public T Value { get; set; }
}

The entire class is parameterized by T.

You can also have both:

class Box<T>
{
    public T Value { get; set; }

    public U Convert<U>(U value)
    {
        return value;
    }
}

Here:

T
↓
class-level type parameter

U
↓
method-level type parameter
37. Generic Type Parameters Are Not Runtime Values

Consider:

Box<int>

The int is a type, not a value.

Compare:

Box<int> box = new Box<int>();

with:

box.Value = 10;

Here:

int
↓
type

10
↓
value

Keeping this distinction clear is important when learning generics.

38. Generics Preserve Type Information

Consider:

List<int> numbers;

The compiler knows:

numbers contains int

Therefore:

numbers.Add(10);

works.

But:

numbers.Add("Hello");

fails at compile time.

This is much safer than:

ArrayList

where values are handled through object.

39. Generics and Value Types

One major advantage of generics is that they can work efficiently with value types.

For example:

List<int>

stores int values without requiring the same boxing behavior that would occur if every value had to be treated as object.

This contributes to both:

type safety
performance

That's one reason generic collections replaced older non-generic collection designs for most modern code.

40. Generic Constraints Don't Convert Types

Suppose:

where T : Animal

This does not mean every T is converted into Animal as the purpose of the constraint.

It means:

T is guaranteed to be Animal or derived from Animal

Therefore members defined by Animal are available.

The actual object can still be:

Dog
Cat
Horse
41. class Constraint and Nullable Reference Types

In modern C#, you may see:

where T : class

and:

where T : class?

These are related to nullable reference type annotations.

For example:

static void Process<T>(T value)
    where T : class
{
}

communicates a non-nullable reference-type constraint under nullable reference type analysis.

Whereas:

where T : class?

allows nullable reference types as the type argument.

This is an advanced distinction, but it is useful to recognize when reading modern C# code.

42. struct Constraint and Nullable Types

A normal:

where T : struct

constraint requires a non-nullable value type.

So:

int
double
DateTime

can satisfy it.

But nullable value types such as:

int?

do not satisfy the ordinary struct constraint in the same way because Nullable<T> itself is not considered a non-nullable value type for that constraint.

The distinction matters when designing generic APIs involving nullable values.

43. Generic Constraints Are About Capabilities

This is the deeper way to think about constraints.

Without constraint:

T
↓
unknown

With:

where T : IPrintable

you know:

T
↓
can Print()

With:

where T : Animal

you know:

T
↓
has Animal's accessible members

With:

where T : new()

you know:

T
↓
can be constructed with new T()

So:

A constraint tells generic code what it is allowed to assume about T.

44. Real-World Generic Repository

A simplified repository:

interface IEntity
{
    int Id { get; }
}
class Repository<T>
    where T : IEntity
{
    private readonly List<T> items = new();

    public void Add(T item)
    {
        items.Add(item);
    }

    public T? FindById(int id)
    {
        foreach (T item in items)
        {
            if (item.Id == id)
            {
                return item;
            }
        }

        return default;
    }
}

Now:

class User : IEntity
{
    public int Id { get; set; }

    public string Name { get; set; }
}

Usage:

Repository<User> repository =
    new Repository<User>();

repository.Add(
    new User
    {
        Id = 1,
        Name = "Alice"
    });

The repository works with User but only relies on the IEntity contract.

This is a very common generic design pattern.

45. default(T)

Generics introduce another important concept:

default(T)

It gives the default value for the type T.

Example:

static T GetDefault<T>()
{
    return default;
}

For:

int

the default is:

0

For:

bool

the default is:

false

For a reference type:

null

So:

default(T)

means:

"Give me the default value appropriate for whatever T actually is."

46. Generic Method With default

Example:

static T Find<T>(T[] values, int index)
{
    if (index < 0 || index >= values.Length)
    {
        return default;
    }

    return values[index];
}

Depending on the type, default could represent:

int       → 0
bool      → false
reference → null
struct    → default struct value

Nullable reference type analysis may require appropriate annotations depending on the API design.

47. Generic Constraints and default

Constraints can make generic behavior more predictable.

For example:

static T Create<T>()
    where T : new()
{
    return new T();
}

Here we don't need:

default(T)

because we know how to create a valid instance.

This demonstrates an important idea:

Generic constraint
       ↓
more information about T
       ↓
more operations become legal
48. Generic Constraints as a Compiler Contract

Think of:

where T : IPrintable

as a contract between you and the compiler:

YOU:
"I promise T implements IPrintable."

COMPILER:
"Then I will allow you to call IPrintable members on T."

If you try to use a type that doesn't satisfy the contract:

compile-time error

This is much better than discovering the problem at runtime.

49. Common Mistakes
Mistake 1 — Assuming T supports everything

This won't generally work:

static void Process<T>(T value)
{
    Console.WriteLine(value.Name);
}

T could be anything.

Use a constraint:

static void Process<T>(T value)
    where T : Person
{
    Console.WriteLine(value.Name);
}
Mistake 2 — Forgetting the constraint for new T()

Wrong:

static T Create<T>()
{
    return new T();
}

Correct:

static T Create<T>()
    where T : new()
{
    return new T();
}
Mistake 3 — Confusing generic type parameter with object

In:

class Box<T>

T isn't an actual object.

It's a placeholder for a type.

T → type
value → object/value of that type
Mistake 4 — Using object when generics are appropriate

Instead of:

object value

often prefer:

T value

when the API needs to preserve the caller's type.

50. Generic Type Constraints Summary
Constraint	Meaning
where T : class	T must be a reference type
where T : class?	T must be a reference type, nullable allowed under nullable analysis
where T : struct	T must be a non-nullable value type
where T : new()	T must have a public parameterless constructor
where T : BaseClass	T must derive from BaseClass or be that type
where T : IInterface	T must implement the interface
Multiple interfaces	T must satisfy all specified interfaces
Base + interfaces + new()	T must satisfy every constraint

52. The Most Important Concept

Don't think of generics as simply:

"A way to avoid writing the same code twice."

That's true, but incomplete.

The deeper idea is:

Generics allow algorithms and data structures to remain type-safe while operating on types that are determined later.

And constraints allow you to say:

"Although T is generic, I know T has these specific capabilities."

That is the real power of generic programming in C#.
