Polymorphism

Polymorphism is the final major concept of 2.1 Deep OOP Concepts.

You already know:

Inheritance
    ↓
A class can derive from another class

Abstraction
    ↓
Define important behavior while hiding unnecessary details

Interfaces
    ↓
Define contracts/capabilities

Now polymorphism connects these ideas.

Polymorphism means that the same operation can produce different behavior depending on the actual object involved.

The most important C# keywords here are:

virtual
override
new
1. What Does Polymorphism Mean?

The word comes from:

Poly  → many
Morphism → forms

So:

One interface/reference, many possible forms of behavior.

Consider:

class Animal
{
    public virtual void MakeSound()
    {
        Console.WriteLine("Some animal sound");
    }
}

class Dog : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Bark");
    }
}

class Cat : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Meow");
    }
}

Now:

Animal dog = new Dog();
Animal cat = new Cat();

dog.MakeSound();
cat.MakeSound();

Output:

Bark
Meow

The reference type is the same:

Animal

But the actual objects are different:

Dog
Cat

Therefore, the same call:

MakeSound()

produces different behavior.

That is polymorphism.

2. The Most Important Mental Model

Consider:

Animal animal = new Dog();

There are two different types involved:

Animal animal
     ↑
Reference type

new Dog()
     ↑
Actual object type

So:

Reference type → Animal
Actual object  → Dog

This distinction is the foundation of runtime polymorphism.

3. Without Polymorphism

Suppose we don't use polymorphism.

class Dog
{
    public void MakeSound()
    {
        Console.WriteLine("Bark");
    }
}

class Cat
{
    public void MakeSound()
    {
        Console.WriteLine("Meow");
    }
}

We need separate code:

Dog dog = new Dog();
dog.MakeSound();

Cat cat = new Cat();
cat.MakeSound();

As the number of animal types grows, the code becomes harder to generalize.

4. With Polymorphism

Create a common base:

class Animal
{
    public virtual void MakeSound()
    {
        Console.WriteLine("Animal sound");
    }
}

Then:

class Dog : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Bark");
    }
}

class Cat : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Meow");
    }
}

Now we can write:

Animal dog = new Dog();
Animal cat = new Cat();

dog.MakeSound();
cat.MakeSound();

Or even:

Animal[] animals =
{
    new Dog(),
    new Cat(),
    new Dog()
};

foreach (Animal animal in animals)
{
    animal.MakeSound();
}

Output:

Bark
Meow
Bark

The loop doesn't need to know the concrete type.

It only knows:

Animal
5. virtual

The virtual keyword tells C#:

This method can be overridden by a derived class.

Example:

class Animal
{
    public virtual void MakeSound()
    {
        Console.WriteLine("Animal sound");
    }
}

Without virtual, a derived class cannot use override on that method.

6. override

The override keyword means:

The derived class is providing a new implementation of an overridable base member.

Example:

class Dog : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Bark");
    }
}

Relationship:

Animal
   │
   └── virtual MakeSound()
             ↑
             │ override
             │
            Dog
7. virtual + override

These two keywords work together.

Base class:

class Animal
{
    public virtual void MakeSound()
    {
        Console.WriteLine("Animal sound");
    }
}

Derived class:

class Dog : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Bark");
    }
}

Think:

virtual
   ↓
"This behavior can be replaced."

override
   ↓
"I am replacing it in this derived class."
8. The Most Important Example
Animal animal = new Dog();

animal.MakeSound();

Question:

Which MakeSound() runs?

There are two possibilities:

Reference type:
Animal

Actual object:
Dog

Because MakeSound() is virtual and Dog uses override:

Dog.MakeSound()

runs.

Output:

Bark

This is runtime polymorphism.

9. Why Is It Called Runtime Polymorphism?

The actual object is determined at runtime.

For example:

Animal animal;

if (DateTime.Now.Day % 2 == 0)
{
    animal = new Dog();
}
else
{
    animal = new Cat();
}

animal.MakeSound();

At compile time, the compiler knows:

animal → Animal reference

But the actual object could be:

Dog

or:

Cat

At runtime, the appropriate overridden implementation is selected.

Conceptually:

animal.MakeSound()
       ↓
What is the actual object?
       ↓
Dog?
       ↓
Dog.MakeSound()

or

Cat?
       ↓
Cat.MakeSound()
10. Compile-Time vs Runtime Polymorphism

You have already studied method overloading.

Method overloading is commonly described as compile-time polymorphism.

Example:

class Calculator
{
    public int Add(int a, int b)
    {
        return a + b;
    }

    public int Add(int a, int b, int c)
    {
        return a + b + c;
    }
}

The compiler determines which method to call based on the arguments.

Add(10, 20)
    ↓
Add(int, int)

Add(10, 20, 30)
    ↓
Add(int, int, int)
Runtime Polymorphism

With overriding:

Animal animal = new Dog();

animal.MakeSound();

The actual object determines the overridden behavior at runtime.

So:

Overloading
    ↓
Compile-time polymorphism

Overriding
    ↓
Runtime polymorphism
11. What Happens Without virtual?

This is extremely important.

Consider:

class Animal
{
    public void MakeSound()
    {
        Console.WriteLine("Animal sound");
    }
}

class Dog : Animal
{
    public void MakeSound()
    {
        Console.WriteLine("Bark");
    }
}

Now:

Animal animal = new Dog();

animal.MakeSound();

The result is:

Animal sound

Why?

Because the base method is not virtual.

The derived method is not overriding it.

It is hiding/shadowing the base method.

The compiler may warn about this because the intention is often unclear.

12. new Method Shadowing

C# provides the new keyword to explicitly say:

I intentionally want to hide the inherited member.

Example:

class Animal
{
    public void MakeSound()
    {
        Console.WriteLine("Animal sound");
    }
}

class Dog : Animal
{
    public new void MakeSound()
    {
        Console.WriteLine("Bark");
    }
}

Now:

Dog dog = new Dog();

dog.MakeSound();

Output:

Bark

But:

Animal animal = new Dog();

animal.MakeSound();

Output:

Animal sound

This is very different from override.

13. override vs new

This is one of the most important comparisons in C# OOP.

override
class Animal
{
    public virtual void MakeSound()
    {
        Console.WriteLine("Animal");
    }
}

class Dog : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Dog");
    }
}

Then:

Animal animal = new Dog();

animal.MakeSound();

Output:

Dog
new
class Animal
{
    public void MakeSound()
    {
        Console.WriteLine("Animal");
    }
}

class Dog : Animal
{
    public new void MakeSound()
    {
        Console.WriteLine("Dog");
    }
}

Then:

Animal animal = new Dog();

animal.MakeSound();

Output:

Animal
14. The Key Difference

Memorize this:

override
    ↓
Runtime polymorphism
    ↓
Actual object matters

new
    ↓
Method hiding
    ↓
Reference type matters

Example:

Animal animal = new Dog();

With override:

Dog method

With new:

Animal method

This difference is critical.

15. Why Does new Behave This Way?

Consider:

Animal animal = new Dog();

The reference says:

Animal

With method hiding:

animal.MakeSound();

the compiler sees the member through the Animal reference.

Because the method isn't virtual, there is no runtime override dispatch.

Therefore:

Animal.MakeSound()

is called.

But with:

virtual + override

the runtime dispatch mechanism can select the derived implementation.

16. Method Hiding Does Not Mean Overriding

This is a common interview question.

These are different:

public override void MakeSound()

and:

public new void MakeSound()
override

The base method must be:

virtual
abstract
override

or another overridable form.

It participates in runtime polymorphism.

new

The base method is hidden.

It does not participate in virtual dispatch as an override.

17. virtual Does Not Mean "Must Override"

Consider:

class Animal
{
    public virtual void Eat()
    {
        Console.WriteLine("Eating");
    }
}

A derived class can override it:

class Dog : Animal
{
    public override void Eat()
    {
        Console.WriteLine("Dog eating");
    }
}

But it doesn't have to.

This is also valid:

class Cat : Animal
{
}

Then:

Cat cat = new Cat();

cat.Eat();

uses the base implementation:

Eating

So:

abstract
   ↓
Must be implemented by concrete derived class

virtual
   ↓
May be overridden

This is a very important distinction.

18. abstract vs virtual
abstract	virtual
No base implementation required	Has a base implementation
Derived concrete class must implement	Derived class may override
Declaring class must be abstract	Declaring class does not have to be abstract
Forces implementation	Allows customization

Example:

Abstract
abstract class Animal
{
    public abstract void MakeSound();
}
Virtual
class Animal
{
    public virtual void MakeSound()
    {
        Console.WriteLine("Animal sound");
    }
}

Mental model:

abstract
    ↓
"You must provide this behavior."

virtual
    ↓
"You may replace this behavior."
19. Override Can Call base

A derived override can call the base implementation.

Example:

class Animal
{
    public virtual void Eat()
    {
        Console.WriteLine("Animal eating");
    }
}

class Dog : Animal
{
    public override void Eat()
    {
        base.Eat();

        Console.WriteLine("Dog eating");
    }
}

Call:

Dog dog = new Dog();

dog.Eat();

Output:

Animal eating
Dog eating

This is useful when the derived class wants to extend rather than completely replace the base behavior.

20. Polymorphism With Arrays

This is where polymorphism becomes practically useful.

class Animal
{
    public virtual void MakeSound()
    {
        Console.WriteLine("Animal sound");
    }
}

class Dog : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Bark");
    }
}

class Cat : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Meow");
    }
}

Now:

Animal[] animals =
{
    new Dog(),
    new Cat(),
    new Dog()
};

Loop:

foreach (Animal animal in animals)
{
    animal.MakeSound();
}

Output:

Bark
Meow
Bark

The loop doesn't need:

if animal is Dog

or:

if animal is Cat

It simply says:

"Animal, make your sound."

Each object knows what to do.

This is one of the biggest practical benefits of polymorphism.

21. Polymorphism Through Methods

Suppose:

void MakeAnimalSound(Animal animal)
{
    animal.MakeSound();
}

Now:

MakeAnimalSound(new Dog());
MakeAnimalSound(new Cat());

The same method works with both.

MakeAnimalSound()
        ↓
      Animal
      /    \
     /      \
   Dog      Cat
    ↓        ↓
  Bark      Meow

The method depends on the base abstraction, not each specific implementation.

22. Polymorphism With Interfaces

Polymorphism is not limited to base classes.

It also works with interfaces.

interface IPayment
{
    void Pay(decimal amount);
}

Implementations:

class CreditCardPayment : IPayment
{
    public void Pay(decimal amount)
    {
        Console.WriteLine("Credit card payment");
    }
}

class UpiPayment : IPayment
{
    public void Pay(decimal amount)
    {
        Console.WriteLine("UPI payment");
    }
}

Now:

IPayment payment = new CreditCardPayment();

payment.Pay(500);

Or:

IPayment payment = new UpiPayment();

payment.Pay(500);

Same interface:

IPayment

Different implementation:

CreditCardPayment
UpiPayment

This is also polymorphism.

23. Why Polymorphism Reduces Coupling

Without polymorphism:

void ProcessPayment(CreditCardPayment payment)
{
}

This method is tied to one concrete implementation.

With polymorphism:

void ProcessPayment(IPayment payment)
{
    payment.Pay(500);
}

Now it can work with:

CreditCardPayment
UpiPayment
BankTransferPayment
PayPalPayment

as long as they implement:

IPayment

So:

Concrete dependency
        ↓
Tighter coupling

Abstraction/interface
        ↓
Looser coupling

This becomes extremely important when we study SOLID, especially the Dependency Inversion Principle.

24. Runtime Dispatch

Let's understand what happens conceptually.

Animal animal = new Dog();

animal.MakeSound();

Base:

class Animal
{
    public virtual void MakeSound()
    {
        Console.WriteLine("Animal");
    }
}

Derived:

class Dog : Animal
{
    public override void MakeSound()
    {
        Console.WriteLine("Dog");
    }
}

Conceptually:

animal.MakeSound()
       ↓
Is MakeSound virtual?
       ↓
Yes
       ↓
What is the actual object?
       ↓
Dog
       ↓
Call Dog.MakeSound()

This behavior is often called virtual dispatch or dynamic dispatch.

You don't manually choose the method.

The runtime dispatch mechanism handles it.

25. A Very Important Example

Consider:

class Animal
{
    public virtual void Speak()
    {
        Console.WriteLine("Animal");
    }
}

class Dog : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Dog");
    }
}

class Cat : Animal
{
    public override void Speak()
    {
        Console.WriteLine("Cat");
    }
}

Now:

Animal a1 = new Dog();
Animal a2 = new Cat();
Animal a3 = new Animal();

Then:

a1.Speak();
a2.Speak();
a3.Speak();

Output:

Dog
Cat
Animal

Same reference type:

Animal

Different actual objects:

Dog
Cat
Animal

Different behavior.

That is the essence of runtime polymorphism.

26. Deep Difference: Reference Type vs Object Type

Consider:

Animal animal = new Dog();
Reference type
Animal

determines what members are available through the reference.

Actual object type
Dog

determines the overridden implementation for virtual members.

So:

Reference type
    ↓
What can I access?

Actual object type
    ↓
Which overridden implementation runs?

This is one of the most important C# OOP mental models.

27. new Method Hiding in More Detail

Consider:

class Animal
{
    public void Speak()
    {
        Console.WriteLine("Animal");
    }
}

class Dog : Animal
{
    public new void Speak()
    {
        Console.WriteLine("Dog");
    }
}

Now:

Dog dog = new Dog();
Animal animal = dog;

Call:

dog.Speak();
animal.Speak();

Output:

Dog
Animal

Why?

Because new does not create an override relationship.

It creates two separate visible members with the same name in different types.

Animal.Speak()
      +
Dog.Speak()

The reference type determines which one is selected.

29. Why Does C# Have new?

Sometimes a derived class intentionally wants to introduce a member with the same name as a base member.

Example:

class BaseLogger
{
    public void Log()
    {
        Console.WriteLine("Base logging");
    }
}

class SpecialLogger : BaseLogger
{
    public new void Log()
    {
        Console.WriteLine("Special logging");
    }
}

This explicitly says:

"I know a base member with this name exists, and I intentionally want to hide it."

However, method hiding should be used carefully because it can make behavior confusing.

If you actually want polymorphic replacement, use:

virtual + override
30. sealed and Polymorphism

There is one more useful keyword related to overriding:

sealed

Suppose:

class Animal
{
    public virtual void Speak()
    {
        Console.WriteLine("Animal");
    }
}

class Dog : Animal
{
    public sealed override void Speak()
    {
        Console.WriteLine("Dog");
    }
}

Now another class:

class SpecialDog : Dog
{
    // Cannot override Speak()
}

because the override was marked:

sealed

Meaning:

This override cannot be overridden further down the inheritance hierarchy.

Mental model:

virtual
   ↓
can override

override
   ↓
provides replacement

sealed override
   ↓
replacement cannot be overridden further

        Console.WriteLine("Bark");
    }

class Cat : Animal

    public override void MakeSound()
    {

    }

Now:

Output:

Bark

Even though Animal itself cannot be instantiated, it provides the abstraction through which polymorphism operates.

33. A Real-World Example

Imagine an order processing system.

abstract class Payment
{
    public abstract void Process(decimal amount);
}

Credit card:

class CreditCardPayment : Payment
{
    public override void Process(decimal amount)
    {
        Console.WriteLine(
            $"Processing credit card payment: {amount}"
        );
    }
}

UPI:

class UpiPayment : Payment
{
    public override void Process(decimal amount)
    {
        Console.WriteLine(
            $"Processing UPI payment: {amount}"
        );
    }
}

Now:

void ProcessOrderPayment(Payment payment)
{
    payment.Process(1000);
}

Call:

ProcessOrderPayment(new CreditCardPayment());
ProcessOrderPayment(new UpiPayment());

The method doesn't need to know the exact payment type.

It only knows:

Payment

This is a major benefit of polymorphic design.

34. Polymorphism Helps Open/Extensible Design

Suppose tomorrow we add:

class BankTransferPayment : Payment
{
    public override void Process(decimal amount)
    {
        Console.WriteLine(
            $"Processing bank transfer: {amount}"
        );
    }
}

The existing method:

void ProcessOrderPayment(Payment payment)
{
    payment.Process(1000);
}

doesn't need to change.

We can simply pass:

ProcessOrderPayment(
    new BankTransferPayment()
);

This idea will become very important when we study:

Open/Closed Principle (OCP)

in the SOLID section.

35. Common Mistakes
Mistake 1 — Using override without virtual

This is invalid:

class Animal
{
    public void Speak()
    {
    }
}

class Dog : Animal
{
    public override void Speak()
    {
    }
}

The base method must be overridable.

For example:

public virtual void Speak()
Mistake 2 — Thinking new is the same as override

It isn't.

override → polymorphic replacement

new → method hiding
Mistake 3 — Forgetting the reference type

This:

Animal animal = new Dog();

has:

Reference → Animal
Object    → Dog

This distinction determines a lot of behavior.

Mistake 4 — Thinking virtual means the method must be overridden

It doesn't.

public virtual void Speak()

means:

The derived class may override it.

abstract is what forces implementation in concrete derived classes.

Mistake 5 — Using new when you actually need polymorphism

If you want:

Animal animal = new Dog();
animal.Speak();

to call the Dog implementation, you generally want:

virtual + override

not:

new
