Lesson 32 — C# Custom Exceptions

Custom exceptions are the next step after understanding normal exception handling.

You already know:

try
{
    // risky code
}
catch (Exception ex)
{
    // handle exception
}

Now the deeper question is:

What if the built-in exception types don't clearly describe the business problem in my application?

For example:

Bank Account
    ↓
Withdraw ₹10,000
    ↓
Balance = ₹3,000
    ↓
Problem!

InvalidOperationException could be used, but it doesn't tell us exactly what happened.

A custom exception can express the domain-specific problem:

InsufficientBalanceException
1. What Is a Custom Exception?

A custom exception is an exception class created by you for a specific application/domain problem.

Example:

public class InsufficientBalanceException : Exception
{
}

Now you have your own exception type:

throw new InsufficientBalanceException();

And you can specifically catch it:

catch (InsufficientBalanceException ex)
{
    Console.WriteLine("Insufficient balance.");
}

The important idea is:

Built-in exception
        ↓
describes common technical problems

Custom exception
        ↓
describes application/domain-specific problems
2. Why Do We Need Custom Exceptions?

Consider a banking application.

if (amount > balance)
{
    throw new InvalidOperationException();
}

This works.

But what does InvalidOperationException actually tell the caller?

Only:

"The operation is invalid."

It doesn't communicate the business reason very precisely.

Instead:

if (amount > balance)
{
    throw new InsufficientBalanceException();
}

Now the exception itself communicates:

InsufficientBalanceException
        ↓
The account does not have enough money

This becomes especially useful in large applications.

3. Exception Classes Are Just Classes

This is one of the most important concepts.

A custom exception is a class.

For example:

public class InsufficientBalanceException : Exception
{
}

Notice:

class InsufficientBalanceException

is normal C# class syntax.

The important part is:

: Exception

This means:

InsufficientBalanceException
          ↓ inherits
       Exception

So your custom exception becomes part of the normal exception hierarchy.

4. Exception Inheritance

The hierarchy looks conceptually like this:

System.Object
     ↓
System.Exception
     ↓
InsufficientBalanceException

You can therefore use:

catch (InsufficientBalanceException ex)

or:

catch (Exception ex)

because:

InsufficientBalanceException
        IS-A
Exception

This is normal inheritance.

5. The Basic Custom Exception

Let's create one.

public class InsufficientBalanceException : Exception
{
}

Then:

public class BankAccount
{
    private decimal balance = 5000;

    public void Withdraw(decimal amount)
    {
        if (amount > balance)
        {
            throw new InsufficientBalanceException();
        }

        balance -= amount;
    }
}

Use it:

try
{
    BankAccount account = new BankAccount();

    account.Withdraw(10000);
}
catch (InsufficientBalanceException)
{
    Console.WriteLine("Not enough balance.");
}

Flow:

Withdraw(10000)
       ↓
amount > balance
       ↓
throw InsufficientBalanceException
       ↓
exception travels up
       ↓
catch (InsufficientBalanceException)
       ↓
handled
6. Why Inherit From Exception?

You should normally derive application-specific exceptions from:

System.Exception

Example:

public class InsufficientBalanceException : Exception
{
}

Not:

public class InsufficientBalanceException
{
}

The second one is just a normal class.

It cannot be thrown as an exception:

throw new InsufficientBalanceException();

because throw expects an exception object.

The compiler therefore requires your throwable type to derive from Exception.

7. Custom Exception With a Message

The basic version isn't very useful because it doesn't contain additional information.

Better:

public class InsufficientBalanceException : Exception
{
    public InsufficientBalanceException(string message)
        : base(message)
    {
    }
}

Now:

throw new InsufficientBalanceException(
    "Account does not have enough balance."
);

Then:

catch (InsufficientBalanceException ex)
{
    Console.WriteLine(ex.Message);
}

Output:

Account does not have enough balance.
8. Understand base(message)

This part is important:

: base(message)

It calls the constructor of the parent class:

Exception

Conceptually:

InsufficientBalanceException constructor
              ↓
       base(message)
              ↓
Exception constructor
              ↓
Exception.Message gets the value

So:

public InsufficientBalanceException(string message)
    : base(message)
{
}

means:

"When creating my custom exception, pass this message to the Exception class."

9. A Better Custom Exception

Real-world custom exceptions commonly provide more than one constructor.

A useful pattern is:

public class InsufficientBalanceException : Exception
{
    public InsufficientBalanceException()
    {
    }

    public InsufficientBalanceException(string message)
        : base(message)
    {
    }

    public InsufficientBalanceException(
        string message,
        Exception innerException)
        : base(message, innerException)
    {
    }
}

Now you can create the exception in different ways.

Without message
throw new InsufficientBalanceException();
With message
throw new InsufficientBalanceException(
    "Balance is too low."
);
With inner exception
throw new InsufficientBalanceException(
    "Withdrawal failed.",
    ex
);
10. Why InnerException Matters

Suppose something fails internally:

try
{
    // database operation
}
catch (Exception ex)
{
    throw new PaymentException(
        "Payment processing failed.",
        ex
    );
}

Now we have:

PaymentException
      ↓
Message:
"Payment processing failed."
      ↓
InnerException
      ↓
Original exception

This lets us add domain meaning while preserving the original technical problem.

11. Exception Wrapping

This pattern is called exception wrapping.

Example:

try
{
    ProcessPayment();
}
catch (Exception ex)
{
    throw new PaymentException(
        "Unable to process payment.",
        ex
    );
}

Why?

Because the lower-level exception might be:

SqlException

But the higher layer may care about:

PaymentException

Conceptually:

Database layer
      ↓
SqlException
      ↓
Service layer
      ↓
PaymentException
      ↓
Application layer

The application gets meaningful domain information while the original exception remains available through:

ex.InnerException
12. Custom Exception With Additional Data

Custom exceptions can also contain domain-specific information.

Example:

public class InsufficientBalanceException : Exception
{
    public decimal Balance { get; }
    public decimal RequestedAmount { get; }

    public InsufficientBalanceException(
        decimal balance,
        decimal requestedAmount)
        : base("Insufficient balance.")
    {
        Balance = balance;
        RequestedAmount = requestedAmount;
    }
}

Now:

throw new InsufficientBalanceException(
    balance,
    amount
);

The caller can inspect:

catch (InsufficientBalanceException ex)
{
    Console.WriteLine($"Balance: {ex.Balance}");
    Console.WriteLine($"Requested: {ex.RequestedAmount}");
}

This is much more useful than putting everything into a string.

13. Complete Example
public class InsufficientBalanceException : Exception
{
    public decimal Balance { get; }
    public decimal RequestedAmount { get; }

    public InsufficientBalanceException(
        decimal balance,
        decimal requestedAmount)
        : base("Insufficient balance.")
    {
        Balance = balance;
        RequestedAmount = requestedAmount;
    }
}

Bank account:

public class BankAccount
{
    private decimal balance;

    public BankAccount(decimal balance)
    {
        this.balance = balance;
    }

    public void Withdraw(decimal amount)
    {
        if (amount <= 0)
        {
            throw new ArgumentOutOfRangeException(
                nameof(amount),
                "Amount must be greater than zero."
            );
        }

        if (amount > balance)
        {
            throw new InsufficientBalanceException(
                balance,
                amount
            );
        }

        balance -= amount;
    }
}

Usage:

try
{
    BankAccount account = new BankAccount(5000);

    account.Withdraw(8000);
}
catch (InsufficientBalanceException ex)
{
    Console.WriteLine(ex.Message);
    Console.WriteLine($"Available: {ex.Balance}");
    Console.WriteLine($"Requested: {ex.RequestedAmount}");
}

Possible output:

Insufficient balance.
Available: 5000
Requested: 8000
14. Custom Exception vs Built-in Exception

This distinction is important.

Built-in exception

Use an existing exception when it already accurately represents the problem.

Example:

if (amount <= 0)
{
    throw new ArgumentOutOfRangeException(nameof(amount));
}

The problem is:

Invalid argument value

A built-in exception already exists for that.

Custom exception

Use a custom exception when the problem has meaningful domain-specific semantics.

Example:

throw new InsufficientBalanceException(
    balance,
    amount
);

The problem is:

Business/domain rule:
account doesn't have enough money
15. Don't Create Custom Exceptions for Everything

This is a very important design principle.

Bad:

public class InvalidNameException : Exception
{
}

public class InvalidAgeException : Exception
{
}

public class InvalidEmailException : Exception
{
}

public class InvalidPhoneException : Exception
{
}

Sometimes these exceptions provide no meaningful value.

For ordinary argument validation, built-in exceptions are usually sufficient:

throw new ArgumentNullException(nameof(name));
throw new ArgumentOutOfRangeException(nameof(age));
throw new ArgumentException(
    "Invalid email format.",
    nameof(email)
);

The goal is not:

"Create as many custom exceptions as possible."

The goal is:

Create a custom exception when it communicates a meaningful domain concept.

16. A Good Mental Rule

Ask yourself:

Can an existing .NET exception accurately describe this problem?

If yes:

Use built-in exception

If no, and the problem represents an important domain/application concept:

Consider custom exception

For example:

Problem	Usually appropriate
Argument is null	ArgumentNullException
Argument value invalid	ArgumentException
Number outside allowed range	ArgumentOutOfRangeException
Operation currently invalid	InvalidOperationException
Collection key missing	KeyNotFoundException
Bank balance insufficient	Custom domain exception
Order already cancelled	Custom domain exception
Payment declined	Potential custom/domain exception
Product unavailable	Potential custom/domain exception

The last cases depend on the architecture and how the application models the domain.

17. Custom Exceptions Should Be Meaningful

Compare:

throw new Exception("Something went wrong.");

with:

throw new PaymentDeclinedException(
    "The payment was declined."
);

The second gives the exception type semantic meaning.

The caller can write:

catch (PaymentDeclinedException)
{
    // payment-specific handling
}

instead of:

catch (Exception ex)
{
    if (ex.Message == "The payment was declined.")
    {
        // ...
    }
}

Never use exception message text as your primary way of determining exception type.

18. Exception Type vs Exception Message

This is a critical distinction.

Bad:

catch (Exception ex)
{
    if (ex.Message == "Insufficient balance.")
    {
        // handle
    }
}

Why is this bad?

Because the message is just text.

It could change because of:

wording changes
localization
punctuation
formatting

Better:

catch (InsufficientBalanceException)
{
    // handle
}

The type communicates the programmatic meaning.

The message communicates human-readable details.

Think:

Exception Type
    ↓
Machine/program meaning

Exception Message
    ↓
Human-readable explanation
19. Catching Custom Exceptions

You can catch the specific exception:

try
{
    account.Withdraw(10000);
}
catch (InsufficientBalanceException ex)
{
    Console.WriteLine(ex.Message);
}

You can also have a fallback:

try
{
    account.Withdraw(10000);
}
catch (InsufficientBalanceException ex)
{
    Console.WriteLine("Balance problem.");
}
catch (Exception ex)
{
    Console.WriteLine("Unexpected error.");
}

Specific first:

InsufficientBalanceException
        ↓
Exception

The more specific handler must appear before the more general one.

20. Custom Exception Hierarchies

You can create your own hierarchy.

For example:

Exception
   ↓
BankingException
   ↓
InsufficientBalanceException

BankingException
   ↓
AccountLockedException

Code:

public class BankingException : Exception
{
    public BankingException(string message)
        : base(message)
    {
    }
}

Then:

public class InsufficientBalanceException : BankingException
{
    public InsufficientBalanceException(string message)
        : base(message)
    {
    }
}

And:

public class AccountLockedException : BankingException
{
    public AccountLockedException(string message)
        : base(message)
    {
    }
}

Now you can catch either:

Specific exception
catch (InsufficientBalanceException ex)
{
}
Whole banking category
catch (BankingException ex)
{
}

This gives your application a meaningful exception hierarchy.

21. Why Would We Create an Intermediate Exception?

Suppose your application has:

BankingException
├── InsufficientBalanceException
├── AccountLockedException
├── DailyLimitExceededException
└── InvalidTransactionException

Now the application can handle all banking problems together:

catch (BankingException ex)
{
    Console.WriteLine(
        $"Banking error: {ex.Message}"
    );
}

Or handle one specifically:

catch (DailyLimitExceededException ex)
{
    // specific handling
}

This is one of the strongest reasons for designing custom exception hierarchies carefully.

22. Don't Use Exceptions for Normal Program Flow

This is a common mistake.

Bad:

try
{
    int number = int.Parse(Console.ReadLine());
}
catch (FormatException)
{
    Console.WriteLine("Invalid number.");
}

For unexpected malformed input, this can be acceptable, but if invalid input is expected and routine, TryParse() is often better:

if (int.TryParse(Console.ReadLine(), out int number))
{
    Console.WriteLine($"Number: {number}");
}
else
{
    Console.WriteLine("Invalid number.");
}

Likewise, don't create custom exceptions simply to replace normal if/else logic.

Bad:

if (age < 18)
{
    throw new UnderAgeException();
}

Whether this is appropriate depends on the domain and layer. If the condition is an exceptional domain failure in that operation, it may be reasonable. If it's just ordinary validation where the caller expects frequent invalid values, returning a validation result may be more appropriate.

The key idea:

Exceptions
    ↓
Exceptional/error situations

Normal validation
    ↓
Often return result / boolean / validation information
23. Custom Exceptions Are Not Automatically "Better"

This is an important design lesson.

Suppose:

public void SetAge(int age)
{
    if (age < 0)
    {
        throw new InvalidAgeException();
    }
}

You could instead use:

public void SetAge(int age)
{
    if (age < 0)
    {
        throw new ArgumentOutOfRangeException(nameof(age));
    }
}

The second may be clearer because .NET already provides an exception specifically for invalid argument ranges.

Custom exception:

More code
+
More types
+
More maintenance

So create one only when the semantic benefit is worth it.

24. Constructor Design

A custom exception commonly supports these constructors:

public class PaymentException : Exception
{
    public PaymentException()
    {
    }

    public PaymentException(string message)
        : base(message)
    {
    }

    public PaymentException(
        string message,
        Exception innerException)
        : base(message, innerException)
    {
    }
}

This gives callers flexibility.

Default
throw new PaymentException();
Message
throw new PaymentException(
    "Payment processing failed."
);
Wrapped exception
throw new PaymentException(
    "Payment service failed.",

);
25. Custom Exception With Domain Data

Suppose an order fails because the product is unavailable.

public class ProductUnavailableException : Exception
{
    public int ProductId { get; }

    public ProductUnavailableException(
        int productId)
        : base("The requested product is unavailable.")
    {
        ProductId = productId;
    }
}

Throw:

throw new ProductUnavailableException(101);

Catch:

catch (ProductUnavailableException ex)
{
    Console.WriteLine(ex.Message);
    Console.WriteLine($"Product ID: {ex.ProductId}");
}

Now the exception contains:

Type:
ProductUnavailableException

Message:
The requested product is unavailable.

Data:
ProductId = 101

This is much more structured than:

throw new Exception(
    "Product 101 is unavailable."
);
26. Exception Data vs Exception Message

Avoid putting structured information only into a message.

Bad:

throw new Exception(
    $"Product {productId} is unavailable."
);

Now the caller would have to parse text to extract:

productId

Better:

public int ProductId { get; }

Then:

throw new ProductUnavailableException(productId);

The information is now strongly typed.

27. A Complete Real-World Mental Model

Imagine an e-commerce system:

User
 ↓
Order Service
 ↓
Payment Service
 ↓
Database / External API

Suppose payment fails.

The lower-level system may throw:

HttpRequestException

The payment service may convert that into:

PaymentException

The order service can then handle:

catch (PaymentException ex)
{
    // mark payment as failed
}

The original technical error is preserved:

PaymentException
      ↓
InnerException
      ↓
HttpRequestException

So:

Low-level technical detail
          ↓
      InnerException

High-level business meaning
          ↓
      Custom exception

This is a powerful pattern in layered applications.

28. What a Good Custom Exception Looks Like

A good custom exception generally has:

✓ Meaningful name
✓ Inherits from Exception
✓ Useful message
✓ Appropriate constructors
✓ InnerException support
✓ Strongly typed domain data when needed
✓ Clear purpose

Example:

public class PaymentDeclinedException : Exception
{
    public string PaymentId { get; }

    public PaymentDeclinedException(string paymentId)
        : base("The payment was declined.")
    {
        PaymentId = paymentId;
    }

    public PaymentDeclinedException(
        string message,
        Exception innerException)
        : base(message, innerException)
    {
    }
}
29. Naming Convention

Custom exception names should normally end with:

Exception

Good:

PaymentException
PaymentDeclinedException
InsufficientBalanceException
OrderAlreadyCancelledException
ProductUnavailableException

Bad:

PaymentError
PaymentProblem
BadPayment
SomethingWrong

The standard convention makes the type immediately recognizable as an exception.

30. Common Mistakes
Mistake 1 — Not inheriting from Exception
public class MyException
{
}

Incorrect for a throwable exception.

Use:

public class MyException : Exception
{
}
Mistake 2 — Using Exception for everything
throw new Exception("Balance insufficient");

This loses semantic type information.

Prefer a meaningful existing or custom exception where appropriate.

Mistake 3 — Creating too many custom exceptions

Don't create a new type for every tiny validation rule.

Use existing .NET exceptions when they already fit.

Mistake 4 — Encoding important data only in the message

Bad:

throw new Exception(
    $"Account {accountId} has balance {balance}."
);

Better:

public string AccountId { get; }
public decimal Balance { get; }
Mistake 5 — Losing the original exception

Bad:

catch (Exception ex)
{
    throw new PaymentException("Payment failed.");
}

The original exception is discarded.

Better:

catch (Exception ex)
{
    throw new PaymentException(
        "Payment failed.",
        ex
    );
}

Now:

PaymentException.InnerException

contains the original exception.

31. Custom Exception vs Return Result

This distinction becomes increasingly important as you build larger applications.

Suppose:

User enters invalid email

This is often expected validation.

A result object or validation message may be appropriate.

But:

Payment provider unexpectedly fails

An exception may be appropriate.

Think:

Expected business validation
        ↓
Result / validation information

Unexpected failure
        ↓
Exception

Meaningful exceptional domain failure
        ↓
Potential custom exception

This is not an absolute rule, but it's a useful architectural guideline.

32. The Deepest Mental Model

Don't think:

"Custom exception = my own error message."

Think:

Custom exception = a typed representation of a meaningful exceptional condition in my application.

There are three layers:

                Exception Type
                       ↓
              WHAT happened?
                       |
                       |
              Exception Data
                       ↓
             WHAT details?
                       |
                       |
              Exception Message
                       ↓
             HOW do we explain it?

Example:

Type:
InsufficientBalanceException

Data:
Balance = 5000
RequestedAmount = 8000

Message:
"Insufficient balance."

That's much more powerful than:

"Something went wrong."
33. Final Example
public class InsufficientBalanceException : Exception
{
    public decimal Balance { get; }
    public decimal RequestedAmount { get; }

    public InsufficientBalanceException(
        decimal balance,
        decimal requestedAmount)
        : base("Insufficient balance for this withdrawal.")
    {
        Balance = balance;
        RequestedAmount = requestedAmount;
    }

    public InsufficientBalanceException(
        string message,
        Exception innerException)
        : base(message, innerException)
    {
    }
}

Usage:

public class BankAccount
{
    private decimal balance;

    public BankAccount(decimal balance)
    {
        this.balance = balance;
    }

    public void Withdraw(decimal amount)
    {
        if (amount <= 0)
        {
            throw new ArgumentOutOfRangeException(
                nameof(amount)
            );
        }

        if (amount > balance)
        {
            throw new InsufficientBalanceException(
                balance,
                amount
            );
        }

        balance -= amount;
    }
}

Application:

try
{
    BankAccount account = new BankAccount(5000);

    account.Withdraw(8000);
}
catch (InsufficientBalanceException ex)
{
    Console.WriteLine(ex.Message);
    Console.WriteLine($"Available: {ex.Balance}");
    Console.WriteLine($"Requested: {ex.RequestedAmount}");
}
catch (Exception ex)
{
    Console.WriteLine("Unexpected error.");
}

Flow:

Withdraw(8000)
      ↓
8000 > 5000
      ↓
throw
      ↓
InsufficientBalanceException
      ↓
search for matching catch
      ↓
catch (InsufficientBalanceException)
      ↓
read Message / Balance / RequestedAmount
      ↓
handled
34. What You Should Remember
Custom Exception
       ↓
class derived from Exception
       ↓
represents a meaningful application/domain failure
       ↓
can have custom constructors
       ↓
can contain structured domain data
       ↓
can preserve InnerException
       ↓
can be caught specifically
Most important rules
Inherit from Exception.
Name it with Exception at the end.
Use an existing .NET exception if it already describes the problem well.
Create custom exceptions for meaningful domain/application conditions.
Don't use exception messages as the exception's identity.
Put important structured data in properties.
Preserve the original exception with InnerException when wrapping.
Don't use exceptions as a replacement for ordinary control flow or routine validation.
