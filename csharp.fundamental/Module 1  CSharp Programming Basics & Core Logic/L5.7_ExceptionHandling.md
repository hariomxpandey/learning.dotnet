Lesson 31 — C# Exception Handling

Part: 5 — Collections & Errors
Topic: Exception Handling
Prerequisite: Methods, try/catch, and basic C# control flow

1. What Is an Exception?

An exception is an object that represents an abnormal condition that occurs while a program is executing.

Example:

int a = 10;
int b = 0;

int result = a / b;

This cannot perform normal integer division.

At runtime, C# throws:

DivideByZeroException

So the flow becomes:

Normal execution
      ↓
10 / 0
      ↓
Exception occurs
      ↓
Normal flow is interrupted
2. Why Do We Need Exception Handling?

Without handling:

int number = 10;
int divisor = 0;

Console.WriteLine(number / divisor);

Console.WriteLine("Program continues...");

The exception interrupts the current execution flow.

With exception handling:

try
{
    int result = number / divisor;
}
catch
{
    Console.WriteLine("Something went wrong.");
}

Console.WriteLine("Program continues...");

Now the program can respond to the exceptional situation.

Mental model:

try
 ↓
Run risky code
 ↓
Exception?
 ├── No → continue normally
 │
 └── Yes
      ↓
    catch
      ↓
    handle exception
      ↓
    continue after handling
3. try

The try block contains code that may throw an exception.

try
{
    int result = 10 / 0;
}

But try by itself is not enough.

A try block must be followed by:

catch

or:

finally

or both.

4. catch

catch handles an exception thrown from the associated try block.

try
{
    int result = 10 / 0;
}
catch
{
    Console.WriteLine("Division failed.");
}

Flow:

try
 ↓
exception
 ↓
catch
 ↓
"Division failed."
5. Basic Example
try
{
    int a = 10;
    int b = 0;

    int result = a / b;

    Console.WriteLine(result);
}
catch
{
    Console.WriteLine("Cannot divide by zero.");
}

Output:

Cannot divide by zero.

The statement after the failing operation inside try is not executed.

6. What Exactly Happens?

Consider:

try
{
    Console.WriteLine("A");

    int result = 10 / 0;

    Console.WriteLine("B");
}
catch
{
    Console.WriteLine("C");
}

Console.WriteLine("D");

Output:

A
C
D

Why isn't B printed?

Because:

A
 ↓
exception
 ↓
remaining try statements are skipped
 ↓
catch
 ↓
D

Once the exception occurs, execution doesn't continue from the next line inside the try block.

7. The Exception Object

You can capture the exception:

try
{
    int result = 10 / 0;
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
}

Here:

Exception
    ↓
base exception type

ex
    ↓
reference to the exception object

The exception object contains information about what happened.

8. ex.Message

Example:

try
{
    int x = 10 / 0;
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
}

Message provides a human-readable description of the exception.

For example, you may see a message related to division by zero.

The exact wording should not be treated as a stable API contract.

9. ex.GetType()

You can inspect the runtime exception type:

catch (Exception ex)
{
    Console.WriteLine(ex.GetType());
}

For a division-by-zero exception, it will identify:

System.DivideByZeroException

This can help when debugging.

10. ex.StackTrace

An exception also contains stack-trace information.

catch (Exception ex)
{
    Console.WriteLine(ex.StackTrace);
}

The stack trace helps identify where the exception propagated through the program.

Conceptually:

Method A
   ↓
Method B
   ↓
Method C
   ↓
exception

The stack trace helps show that execution path.

11. Specific Exception Types

C# has many exception types.

Examples:

DivideByZeroException
NullReferenceException
IndexOutOfRangeException
ArgumentException
ArgumentNullException
InvalidOperationException
FormatException
KeyNotFoundException
InvalidCastException

Different exceptions represent different kinds of problems.

12. Catching a Specific Exception

Instead of:

catch (Exception ex)
{
}

you can catch a specific type:

try
{
    int result = 10 / 0;
}
catch (DivideByZeroException ex)
{
    Console.WriteLine("Cannot divide by zero.");
}

This is generally better when you know exactly which exception you want to handle.

13. Why Specific Catch Blocks Are Better

Consider:

try
{
    // some operation
}
catch (DivideByZeroException)
{
    // division problem
}
catch (FormatException)
{
    // invalid format
}

Now the program can respond differently depending on the actual problem.

Mental model:

Exception
    ↓
What type?
    ↓
DivideByZeroException → first catch
FormatException       → second catch
14. Multiple catch Blocks

You can have multiple catch blocks:

try
{
    // risky code
}
catch (DivideByZeroException)
{
    Console.WriteLine("Division error.");
}
catch (FormatException)
{
    Console.WriteLine("Format error.");
}
catch (Exception)
{
    Console.WriteLine("Some other error.");
}

Only one matching catch block handles a particular exception as the exception propagates through this catch chain.

15. Catch Order Matters

This is important.

Consider:

try
{
}
catch (Exception)
{
}
catch (DivideByZeroException)
{
}

This is invalid.

Why?

Because:

DivideByZeroException
       ↓
inherits from
       ↓
Exception

So the first catch already catches it.

The more specific exception must come first:

catch (DivideByZeroException)
{
}
catch (Exception)
{
}

Mental rule:

Specific
  ↓
General
16. The Exception Hierarchy

At a simplified level:

object
  ↓
Exception
  ├── SystemException
  │      ├── DivideByZeroException
  │      ├── NullReferenceException
  │      ├── IndexOutOfRangeException
  │      └── ...
  │
  └── Other exception categories

This is why:

catch (Exception ex)

can catch many exception types.

Exception is a broad base type.

17. Should We Always Catch Exception?

No.

Avoid blindly doing:

try
{
    // everything
}
catch (Exception)
{
    // ignore everything
}

This can hide programming bugs.

Prefer handling exceptions where you can actually do something meaningful.

For example:

try
{
    int number = int.Parse(input);
}
catch (FormatException)
{
    Console.WriteLine("Please enter a valid number.");
}

Here the program knows how to recover.

18. finally

finally is used for cleanup code that should execute after the try/catch processing.

Example:

try
{
    Console.WriteLine("Try");
}
catch
{
    Console.WriteLine("Catch");
}
finally
{
    Console.WriteLine("Finally");
}

Output:

Try
Finally

If an exception occurs:

Try
Catch
Finally
19. Basic finally Flow

Think:

try
 ↓
 ├── success ───────┐
 │                   ↓
 │                finally
 │
 └── exception
       ↓
     catch
       ↓
    finally

The finally block is intended for cleanup that should occur regardless of whether the operation succeeded or an exception was handled.

20. Example With Exception
try
{
    int result = 10 / 0;
}
catch (DivideByZeroException)
{
    Console.WriteLine("Error.");
}
finally
{
    Console.WriteLine("Cleanup.");
}

Output:

Error.
Cleanup.
21. finally Without catch

You can have:

try
{
    // code
}
finally
{
    // cleanup
}

This is valid.

But if the try throws an exception, the exception is not swallowed.

Conceptually:

try
 ↓
exception
 ↓
finally
 ↓
exception continues propagating

This pattern can be useful when you need cleanup but want the exception to continue to the caller.

22. try-catch-finally

The complete pattern:

try
{
    // risky operation
}
catch (SpecificException ex)
{
    // handle known problem
}
finally
{
    // cleanup
}

Each part has a different responsibility:

try
 ↓
attempt operation

catch
 ↓
handle exception

finally
 ↓
cleanup
23. throw

Sometimes you need to explicitly throw an exception.

Use:

throw;

or:

throw new Exception("Something went wrong.");

Example:

int age = -5;

if (age < 0)
{
    throw new ArgumentException("Age cannot be negative.");
}

Here the program deliberately creates an exception because the input violates a rule.

24. throw new

Example:

throw new ArgumentException("Invalid age.");

Conceptually:

new ArgumentException(...)
        ↓
create exception object
        ↓
throw
        ↓
search for matching catch

If no suitable catch exists in the current call chain, the exception continues propagating upward.

25. throw; vs throw ex;

This is a very important distinction.

Suppose:

try
{
    DoSomething();
}
catch (Exception ex)
{
    throw;
}

This rethrows the same exception while preserving its original stack-trace information.

Prefer:

throw;

when you want to rethrow the current exception.

26. Why throw ex; Is Different

Consider:

catch (Exception ex)
{
    throw ex;
}

This changes the stack-trace behavior and can obscure the original location where the exception occurred.

So when rethrowing the current exception:

throw;

is generally the correct form.

Remember:

throw;
   ↓
rethrow current exception

throw new Exception(...);
   ↓
create and throw a new exception
27. Exception Propagation

This is one of the most important concepts.

Suppose:

static void MethodC()
{
    int x = 10 / 0;
}

And:

static void MethodB()
{
    MethodC();
}

And:

static void MethodA()
{
    MethodB();
}

And:

static void Main()
{
    MethodA();
}

The flow is:

Main
 ↓
MethodA
 ↓
MethodB
 ↓
MethodC
 ↓
exception

If MethodC doesn't handle it:

MethodC
   ↓
MethodB
   ↓
MethodA
   ↓
Main

The exception propagates up the call stack until a matching handler is found.

28. Handling at a Higher Level

Example:

static void MethodC()
{
    int result = 10 / 0;
}

static void MethodB()
{
    MethodC();
}

static void Main()
{
    try
    {
        MethodB();
    }
    catch (DivideByZeroException)
    {
        Console.WriteLine("Handled in Main.");
    }
}

The exception is thrown in:

MethodC

but handled in:

Main

This is valid.

29. Why Not Catch Everywhere?

Bad design:

void MethodA()
{
    try
    {
        MethodB();
    }
    catch
    {
    }
}

Then:

void MethodB()
{
    try
    {
        MethodC();
    }
    catch
    {
    }
}

And so on.

This can make errors disappear without actually being handled.

A better approach is:

Handle an exception at the level where you have enough context to recover from it or meaningfully report it.

30. Example — User Input

Suppose:

Console.Write("Enter age: ");

string input = Console.ReadLine();

int age = int.Parse(input);

If the user enters:

abc

int.Parse() throws:

FormatException

We can handle it:

try
{
    Console.Write("Enter age: ");

    string input = Console.ReadLine();

    int age = int.Parse(input);

    Console.WriteLine($"Age: {age}");
}
catch (FormatException)
{
    Console.WriteLine("Please enter a valid number.");
}
31. Parse() vs TryParse()

There is an important design point here.

You could use:

int.Parse(input);

which throws when parsing fails.

But for ordinary user input, a better approach is often:

if (int.TryParse(input, out int age))
{
    Console.WriteLine($"Age: {age}");
}
else
{
    Console.WriteLine("Invalid age.");
}

Why?

Because invalid user input is often an expected condition, not an exceptional one.

Mental distinction:

Expected invalid input
        ↓
TryParse()

Unexpected exceptional condition
        ↓
Exception handling

This is an important exception-handling design principle.

32. Common Exception Types
DivideByZeroException
int result = 10 / 0;
IndexOutOfRangeException
int[] numbers = { 10, 20 };

Console.WriteLine(numbers[5]);
NullReferenceException

Example:

string name = null;

Console.WriteLine(name.Length);

The variable doesn't reference a usable string object.

FormatException

Example:

int.Parse("abc");
InvalidCastException

Example:

object value = "Hello";

int number = (int)value;
KeyNotFoundException

Example:

Dictionary<int, string> data = new();

Console.WriteLine(data[100]);

if key 100 doesn't exist.

33. ArgumentException

Used when an argument passed to a method is invalid.

Example:

static void SetAge(int age)
{
    if (age < 0)
    {
        throw new ArgumentException("Age cannot be negative.");
    }
}

More specific variants include:

ArgumentNullException
ArgumentOutOfRangeException

For example:

ArgumentOutOfRangeException

is appropriate when a value is outside an allowed range.

34. ArgumentNullException

Example:

static void PrintName(string name)
{
    if (name == null)
    {
        throw new ArgumentNullException(nameof(name));
    }

    Console.WriteLine(name);
}

nameof(name) produces:

name

without hardcoding the parameter name as a string.

35. InvalidOperationException

This generally indicates:

The method call is invalid for the object's current state.

Example:

List<int> numbers = new List<int>();

int first = numbers[0];

More broadly, InvalidOperationException is commonly used when an operation is not valid given the current state of an object or system.

36. Don't Use Exceptions for Normal Control Flow

Avoid code like:

try
{
    // intentionally cause exception
}
catch
{
    // use exception as normal decision mechanism
}

For example, don't repeatedly use exceptions to check whether a value can be parsed when:

int.TryParse(...)

already exists.

Prefer:

Normal expected condition
    ↓
normal control flow

Unexpected exceptional condition
    ↓
exception
37. Exception Filtering

C# allows a when condition on a catch.

Example:

try
{
    // code
}
catch (Exception ex) when (ex.Message.Contains("network"))
{
    Console.WriteLine("Network-related problem.");
}

The catch only applies if the filter evaluates to true.

Conceptually:

Exception
   ↓
matching type?
   ↓
when condition?
   ↓
true → catch
false → continue searching

This is useful in advanced exception handling, though it should be used carefully.

38. InnerException

Sometimes one exception is caused by another exception.

An exception can contain:

ex.InnerException

Conceptually:

Outer Exception
      ↓
Inner Exception
      ↓
Original cause

Example:

Exception outer =
    new Exception(
        "Operation failed.",
        new InvalidOperationException("Original problem.")
    );

Then:

Console.WriteLine(outer.Message);
Console.WriteLine(outer.InnerException?.Message);

This is useful when higher-level code wraps a lower-level failure with additional context.

39. Wrapping Exceptions

Suppose a lower-level operation throws:

SqlException

A service layer may want to provide domain/application context:

try
{
    // database operation
}
catch (Exception ex)
{
    throw new Exception(
        "Failed to load customer data.",
        ex
    );
}

Now:

Outer exception
"Failed to load customer data."
        ↓
InnerException
original exception

This preserves the underlying cause.

In real applications, you'd normally use a more appropriate exception type rather than blindly creating Exception.

40. Custom Exceptions

C# allows you to create your own exception types.

Example:

class InvalidAgeException : Exception
{
    public InvalidAgeException(string message)
        : base(message)
    {
    }
}

Then:

throw new InvalidAgeException("Age is invalid.");

This is useful when your application has a meaningful domain-specific error condition.

We'll cover custom exceptions as the next dedicated topic, so don't treat this section as the complete custom-exception lesson.

41. finally and Resource Cleanup

Historically, finally was commonly used for cleanup:

Resource resource = AcquireResource();

try
{
    resource.Use();
}
finally
{
    resource.Dispose();
}

Modern C# provides cleaner resource-management syntax:

using (Resource resource = AcquireResource())
{
    resource.Use();
}

or:

using Resource resource = AcquireResource();

resource.Use();

These forms are designed around IDisposable and ensure disposal even when an exception occurs.

You already encountered IDisposable and finally concepts while studying finalizers.

The important distinction is:

finally
 ↓
general cleanup/final execution block

Dispose / using
 ↓
structured resource management
42. Exception Handling Does Not Mean "Ignore Errors"

This is a common beginner mistake:

try
{
    DoSomething();
}
catch
{
}

This is called an empty catch.

It silently ignores the exception.

Problems:

Exception occurs
      ↓
ignored
      ↓
program continues
      ↓
actual problem becomes difficult to diagnose

Unless there is a very specific reason, don't silently swallow exceptions.

43. Logging vs Showing Errors

In real applications, you usually shouldn't expose raw exception details to users.

Bad user-facing approach:

System.NullReferenceException:
Object reference not set...

Instead:

Something went wrong. Please try again.

while logging the technical exception internally.

Conceptually:

Exception
   ├── user → safe meaningful message
   │
   └── logs → technical details

The exact logging mechanism depends on the application.

44. Preserve the Original Exception

Suppose:

catch (Exception ex)
{
    throw;
}

This preserves the exception's existing propagation information.

If you need to add context:

catch (Exception ex)
{
    throw new Exception("Loading student failed.", ex);
}

Now the original exception is available through:

ex.InnerException

Avoid replacing useful diagnostic information with a completely unrelated exception.

45. Exception Handling Flow

Here's the complete mental model:

                 Method Call
                     │
                     ▼
                   try
                     │
              ┌──────┴──────┐
              │             │
          No exception   Exception
              │             │
              │             ▼
              │       Find matching catch
              │             │
              │       ┌──────┴──────┐
              │       │             │
              │     found        not found
              │       │             │
              │       ▼             ▼
              │     catch       propagate upward
              │       │
              └───────┴─────────────┐
                                    ▼
                                 finally
                                    │
                                    ▼
                               continue/return
46. The Most Important Rules
1. Exception = object representing an exceptional condition.

2. try contains code that may throw.

3. catch handles a matching exception.

4. finally is used for cleanup/final execution.

5. Catch specific exceptions when you know how to handle them.

6. Put specific catch blocks before general catch blocks.

7. Exception can propagate up the call stack.

8. throw creates or rethrows an exception.

9. throw; rethrows the current exception.

10. throw new ... creates a new exception.

11. TryParse() is often better than Parse() when invalid
    input is an expected possibility.

12. Don't use exceptions for ordinary control flow.

13. Don't silently swallow exceptions without a good reason.

14. InnerException can preserve the underlying cause.

15. Handle an exception at the level where meaningful recovery
    or context is available.
47. Complete Example
using System;

class Program
{
    static void Main()
    {
        try
        {
            Console.Write("Enter first number: ");
            int first = int.Parse(Console.ReadLine());

            Console.Write("Enter second number: ");
            int second = int.Parse(Console.ReadLine());

            int result = first / second;

            Console.WriteLine($"Result: {result}");
        }
        catch (FormatException)
        {
            Console.WriteLine("Please enter valid numbers.");
        }
        catch (DivideByZeroException)
        {
            Console.WriteLine("Second number cannot be zero.");
        }
        finally
        {
            Console.WriteLine("Operation finished.");
        }
    }
}

Possible flows:

Valid input
Enter first number: 20
Enter second number: 5
Result: 4
Operation finished.
Invalid format
Enter first number: abc
Please enter valid numbers.
Operation finished.
Division by zero
Enter first number: 20
Enter second number: 0
Second number cannot be zero.
Operation finished.
