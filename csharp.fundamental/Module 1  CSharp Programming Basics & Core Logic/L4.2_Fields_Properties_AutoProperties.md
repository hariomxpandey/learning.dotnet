Fields in C#

Module: 1 — C# Programming Basics & Core Logic
Section: 1.4 Core Object-Oriented Programming
Prerequisite: Classes and Objects

1. What Is a Field?

A field is a variable declared directly inside a class or struct.

Example:

class Student
{
    public string name;
    public int age;
}

Here:

name → field
age  → field

They belong to the Student type.

Remember:

Local variable
    ↓
declared inside a method/block

Field
    ↓
declared directly inside a class/struct
2. Field vs Local Variable

This distinction is very important.

Local variable
void Study()
{
    int hours = 5;
}

hours is a local variable.

Field
class Student
{
    int age;
}

age is a field.

Visual:

class Student
{
    // Field
    int age;

    void Study()
    {
        // Local variable
        int hours = 5;
    }
}
3. Why Do We Need Fields?

Objects need to remember their state.

Example:

class Student
{
    public string name;
    public int age;
}

Create an object:

Student student = new Student();

student.name = "Hariom";
student.age = 22;

The object now has state:

student
│
├── name → "Hariom"
└── age  → 22

The fields hold the object's data.

4. Fields Belong to Objects

By default, a non-static field is an instance field.

Example:

class Student
{
    public string name;
    public int age;
}

Create two objects:

Student s1 = new Student();
Student s2 = new Student();

Each object has its own fields:

s1
├── name
└── age

s2
├── name
└── age

Therefore:

s1.name = "Hariom";
s2.name = "Aman";

is perfectly normal.

5. Instance Field

An instance field belongs to an instance/object.

Example:

class Car
{
    public string brand;
    public int speed;
}

Create:

Car car1 = new Car();
Car car2 = new Car();

Each object has its own:

brand
speed

So:

car1.speed = 100;
car2.speed = 150;

results in:

car1 → speed = 100
car2 → speed = 150
6. Important: Fields Are Not Automatically Shared

Consider:

class Student
{
    public string name;
}

Then:

Student s1 = new Student();
Student s2 = new Student();

s1.name = "Hariom";
s2.name = "Aman";

The values are separate.

s1.name → Hariom

s2.name → Aman

Why?

Because name is an instance field.

7. Field Initialization

A field can be initialized when declared.

class Student
{
    public string name = "Unknown";
    public int age = 0;
}

Now:

Student student = new Student();

Console.WriteLine(student.name);
Console.WriteLine(student.age);

Output:

Unknown
0

The initial value becomes the object's starting state.

8. Default Field Values

If you don't explicitly initialize a field, C# gives it a default value.

Example:

class Student
{
    public int age;
    public double marks;
    public bool passed;
    public string name;
}

Typical defaults:

Type	Default value
int	0
double	0
bool	false
char	'\0'
Reference types such as string	null

So:

Student student = new Student();

Console.WriteLine(student.age);
Console.WriteLine(student.marks);
Console.WriteLine(student.passed);
Console.WriteLine(student.name == null);

Conceptually:

age    → 0
marks  → 0
passed → false
name   → null
9. Why Do Fields Get Default Values?

When an object is created, its instance storage is initialized.

This means you don't get arbitrary garbage values for ordinary C# fields.

For example:

class Account
{
    public double balance;
}

Creating:

Account account = new Account();

gives the field its default value:

balance → 0
10. Fields Can Be Different Types

A class can contain many fields:

class Employee
{
    public string name;
    public int age;
    public double salary;
    public bool isActive;
}

Object state:

Employee
│
├── name
├── age
├── salary
└── isActive
11. Field Access

If a field is accessible, use the dot operator:

employee.name
employee.age
employee.salary

Example:

Employee employee = new Employee();

employee.name = "Hariom";
employee.age = 22;
employee.salary = 50000;

The dot means:

object/reference
      ↓
access member
12. Access Modifiers on Fields

Fields can have access modifiers.

For example:

class Student
{
    public string name;
    private int age;
}

name can be accessed from outside the class if otherwise accessible.

age cannot be directly accessed from unrelated outside code because it is private.

Example:

Student student = new Student();

student.name = "Hariom";  // Valid

student.age = 22;        // Error

We'll study access modifiers and encapsulation more deeply later.

13. Why private Fields Are Common

A common OOP design is:

class BankAccount
{
    private double balance;
}

Instead of allowing anyone to do:

account.balance = -100000;

we can control changes through methods or properties.

For example:

class BankAccount
{
    private double balance;

    public void Deposit(double amount)
    {
        if (amount > 0)
        {
            balance += amount;
        }
    }
}

Now the class controls how its internal data changes.

This is the beginning of encapsulation.

14. Field + Method

Fields and methods often work together.

class Counter
{
    private int count;

    public void Increment()
    {
        count++;
    }

    public void Display()
    {
        Console.WriteLine(count);
    }
}

Usage:

Counter counter = new Counter();

counter.Increment();
counter.Increment();
counter.Increment();

counter.Display();

Output:

3

The field stores state:

count

The method changes that state:

Increment()
15. Instance Field + Instance Method

This is a very common OOP pattern:

Object
│
├── State
│   └── fields
│
└── Behavior
    └── methods

Example:

class Car
{
    private int speed;

    public void Accelerate()
    {
        speed += 10;
    }

    public void ShowSpeed()
    {
        Console.WriteLine(speed);
    }
}

The object owns:

speed

and provides behavior:

Accelerate()
ShowSpeed()
16. Static Fields

Now an important distinction.

A field can be static.

Example:

class Student
{
    public static int count;
}

A static field belongs to the type itself, rather than separately to each object.

Think:

Instance field:

Student
├── s1 → name
├── s2 → name
└── s3 → name

versus:

Static field:

Student
└── count

There is one static field associated with the type.

17. Instance Field vs Static Field

Example:

class Student
{
    public string name;
    public static int count;
}

Here:

name
→ instance field

count
→ static field

If:

Student s1 = new Student();
Student s2 = new Student();

Then conceptually:

s1
└── name

s2
└── name

Student
└── count
18. Accessing a Static Field

Static members are normally accessed through the type:

Student.count

Example:

class Student
{
    public static int count;
}

Then:

Student.count = 10;

Console.WriteLine(Student.count);

You don't need:

Student student = new Student();

to access the static field.

This connects directly to the static concept we studied earlier.

19. Static Field Example

A classic use case is counting objects.

class Student
{
    public static int count;

    public Student()
    {
        count++;
    }
}

Now:

Student s1 = new Student();
Student s2 = new Student();
Student s3 = new Student();

Console.WriteLine(Student.count);

Output:

3

Each constructor execution increments the same static field.

20. Visualizing Static vs Instance
Student type
│
└── static count = 3
        ↑
        │ shared
        │
    ┌───┴────┐
    ↓        ↓
   s1       s2       s3
   │         │        │
 name      name     name

Instance fields:

s1.name
s2.name
s3.name

are separate.

Static field:

Student.count

is shared by the type.

21. A Common Mistake

Consider:

class Student
{
    public static int count;
}

This is wrong:

Student s1 = new Student();

s1.count = 10;

Although C# may allow access to a static member through an instance in some contexts, the preferred and clear form is:

Student.count = 10;

Use the type name for static members.

Static → Type.Member
Instance → object.Member
22. const Fields

Another important kind of field-like member is const.

Example:

class MathConstants
{
    public const double Pi = 3.14159;
}

A constant represents a value that cannot be changed after it is defined.

Usage:

Console.WriteLine(MathConstants.Pi);

A const member is implicitly static.

So:

const
  ↓
constant value
  ↓
access through type
23. const vs Static Field

Compare:

public static int count;

and:

public const int MaxStudents = 100;
Static field

Can normally change:

count = 10;
count = 20;
Constant

Cannot change:

MaxStudents = 200; // Error

So:

static field
→ shared variable

const
→ compile-time constant
24. readonly Fields

Another important field modifier is:

readonly

Example:

class Student
{
    public readonly int id;

    public Student(int id)
    {
        this.id = id;
    }
}

A readonly instance field can be assigned during declaration or in an instance constructor.

After construction, it cannot normally be reassigned.

Example:

Student student = new Student(101);

// student.id = 202; // Error
25. Why readonly Is Useful

Suppose every student should have an ID that shouldn't change after creation.

class Student
{
    public readonly int id;

    public Student(int id)
    {
        this.id = id;
    }
}

Then:

Student student = new Student(101);

The object gets:

id = 101

and the field is intended to remain unchanged afterward.

26. const vs readonly

This distinction is important.

const	readonly
Compile-time constant	Runtime-assigned field allowed
Must be initialized as part of declaration	Can be initialized in constructor
Implicitly static	Can be instance or static
Cannot change	Cannot normally change after allowed initialization

Example:

public const int MaxAge = 100;

versus:

public readonly int id;

public Student(int id)
{
    this.id = id;
}

Mental model:

const
→ same fixed value defined by the type

readonly
→ value fixed for that object's lifetime after initialization
27. Static Readonly

You can also combine:

static readonly

Example:

class Configuration
{
    public static readonly string AppName = "MyApp";
}

This means:

static
→ belongs to the type

readonly
→ cannot normally be reassigned after its initialization

Unlike const, a static readonly field can be initialized at runtime, including in a static constructor.

28. Field Initialization Order — Basic Idea

Consider:

class Student
{
    public int age = 22;
    public string name = "Hariom";
}

When an object is created, its instance fields are initialized as part of object construction before the constructor body runs.

This becomes important when we study constructors.

For now remember:

new Student()
    ↓
object initialization
    ↓
constructor execution

We'll revisit this in much more detail.

29. this and Fields

Inside an instance method, you can use:

this

to refer to the current object.

Example:

class Student
{
    private string name;

    public void SetName(string name)
    {
        this.name = name;
    }
}

Here there are two names:

parameter name
field name

this.name means:

current object's field

while:

name

means the parameter in this context.

30. Why this Is Useful

Without this, this would be confusing:

public void SetName(string name)
{
    name = name;
}

Both references resolve to the parameter.

The field isn't being assigned.

Correct:

public void SetName(string name)
{
    this.name = name;
}

Visual:

this.name
   ↓
field

name
   ↓
parameter
31. Fields and Object State

Let's build a complete example:

class BankAccount
{
    private string accountHolder;
    private double balance;

    public void Deposit(double amount)
    {
        balance += amount;
    }

    public void DisplayBalance()
    {
        Console.WriteLine(balance);
    }
}

The object's state is:

BankAccount object
│
├── accountHolder
└── balance

Methods operate on that state.

This is a fundamental OOP pattern.

32. Why Public Fields Are Usually Not Ideal

You might write:

class BankAccount
{
    public double balance;
}

Then anyone can do:

account.balance = -1000000;

The class has no control.

Better design:

class BankAccount
{
    private double balance;

    public void Deposit(double amount)
    {
        if (amount > 0)
        {
            balance += amount;
        }
    }
}

Now the class controls modifications.

This leads directly to:

Encapsulation

We'll study that as its own topic.

33. Field vs Property

Don't confuse these.

Field
private string name;
Property
public string Name { get; set; }

A property is not simply another syntax for a field.

A property provides accessors:

get
set

and can contain logic.

We'll study properties deeply in the next lessons.

For now:

Field
→ stores data directly

Property
→ provides controlled access to data
34. Fields Inside Classes

A typical beginner class might look like:

    private double marks;

        Console.WriteLine(name);

35. Static Field Example in Detail

Consider:

class Employee
{
    public string name;
    public static int employeeCount;

    public Employee(string name)
    {
        this.name = name;
        employeeCount++;
    }

Create:

36. Instance Field vs Static Field — Core Difference
Feature	Instance Field	Static Field
Belongs to	Object	Type
Copies	One per object	One associated with type
Access	object.field	Class.field
Stores	Object-specific state	Shared type-level state
Requires object?	Yes, for normal access	No

Example:

class Student
{
    public string name;
    public static int totalStudents;
}

Use:

student.name

for instance state.

Use:

Student.totalStudents

for shared type-level state.

If:

Properties in C#

Module: 1 — C# Programming Basics & Core Logic
Section: 1.4 Core Object-Oriented Programming
Prerequisite: Classes, Objects, and Fields

1. Why Do We Need Properties?

In the previous lesson, we used fields:

class Student
{
    public string name;
    public int age;
}

Then outside the class:

Student student = new Student();

student.name = "Hariom";
student.age = 22;

This works.

But there is a problem.

Anyone can directly change the fields:

student.age = -500;

That doesn't make logical sense.

The class has no control over the value.

This is one of the reasons C# provides properties.

Field
  ↓
stores data

Property
  ↓
controls access to data
2. What Is a Property?

A property is a class member that provides controlled access to a value.

Basic syntax:

public string Name
{
    get;
    set;
}

Example:

class Student
{
    public string Name
    {
        get;
        set;
    }
}

Now:

Student student = new Student();

student.Name = "Hariom";

Console.WriteLine(student.Name);

Output:

Hariom
3. Property Has get and set

Consider:

public string Name
{
    get;
    set;
}

There are two accessors.

get

Reads the value.

Console.WriteLine(student.Name);

Conceptually:

Name
 ↓
get
 ↓
return value
set

Assigns a value.

student.Name = "Hariom";

Conceptually:

"Hariom"
   ↓
set
   ↓
Name
4. Property Syntax Breakdown

Look carefully:

public string Name
{
    get;
    set;
}

Breakdown:

public
  ↓
access modifier

string
  ↓
property type

Name
  ↓
property name

get
  ↓
read access

set
  ↓
write access
5. Property vs Field

Field:

public string name;

Property:

public string Name
{
    get;
    set;
}

They are not the same thing.

Field

A field directly represents stored member data.

Property

A property provides an interface for accessing a value.

Think:

Field
  ↓
storage

Property
  ↓
access mechanism

A property may use an automatically generated backing field, or it may execute custom logic.

6. Why Properties Are Better Than Public Fields

Suppose:

class Student
{
    public int age;
}

Anyone can do:

student.age = -100;

Now use a property:

class Student
{
    private int age;

    public int Age
    {
        get
        {
            return age;
        }

        set
        {
            if (value >= 0)
            {
                age = value;
            }
        }
    }
}

Now:

student.Age = 22;

works.

But:

student.Age = -100;

is rejected by the property's logic.

This is controlled access.

7. The value Keyword

Inside a property set, C# provides a special keyword:

value

Example:

public int Age
{
    get
    {
        return age;
    }

    set
    {
        age = value;
    }
}

If we write:

student.Age = 22;

then conceptually:

value = 22

So:

age = value;

means:

age = 22;
8. Full Property With Backing Field

Classic property pattern:

class Student
{
    private string name;

    public string Name
    {
        get
        {
            return name;
        }

        set
        {
            name = value;
        }
    }
}

Usage:

Student student = new Student();

student.Name = "Hariom";

Console.WriteLine(student.Name);

Output:

Hariom

Structure:

Student
│
├── private name       ← backing field
│
└── Name               ← property
    ├── get
    └── set
9. What Is a Backing Field?

A backing field is a field used to store the value represented by a property.

Example:

private string name;

public string Name
{
    get
    {
        return name;
    }

    set
    {
        name = value;
    }
}

Here:

name

is the backing field.

And:

Name

is the property.

Relationship:

Property
   │
   ├── get → reads backing field
   │
   └── set → writes backing field
10. Auto-Implemented Properties

C# gives us a shorter syntax.

Instead of:

private string name;

public string Name
{
    get
    {
        return name;
    }

    set
    {
        name = value;
    }
}

we can write:

public string Name
{
    get;
    set;
}

This is an auto-implemented property.

C# automatically provides the hidden backing storage.

11. Why Auto-Properties Exist

Most properties don't need custom logic.

For example:

class Student
{
    public string Name { get; set; }
    public int Age { get; set; }
}

This is much cleaner than writing explicit backing fields when no special behavior is required.

Usage:

Student student = new Student();

student.Name = "Hariom";
student.Age = 22;
12. Modern Property Syntax

You will commonly see:

public string Name { get; set; }

instead of:

public string Name
{
    get;
    set;
}

Both represent the same basic auto-property concept.

The shorter form is standard C# style.

13. Read-Only Property

Sometimes we want users to read a value but not directly change it.

Use only:

get

Example:

class Student
{
    public string Name { get; }
}

Now:

Console.WriteLine(student.Name);

is allowed.

But:

student.Name = "Aman";

is not allowed from ordinary external code.

14. Read-Only Property With Constructor

A very useful pattern:

class Student
{
    public int Id { get; }

    public Student(int id)
    {
        Id = id;
    }
}

Create:

Student student = new Student(101);

Then:

Console.WriteLine(student.Id);

works.

But:

student.Id = 202;

doesn't compile.

Conceptually:

Constructor
   ↓
sets Id
   ↓
object created
   ↓
Id can be read
   ↓
external code cannot assign it
15. get-Only Does Not Mean "Immutable Forever"

Be precise here.

Consider:

public int Id { get; }

The property has no setter.

But the value can be assigned during initialization, such as in a constructor.

Example:

class Student
{
    public int Id { get; }

    public Student(int id)
    {
        Id = id;
    }
}

After construction, external code cannot assign it through the property.

16. Private Setter

Another useful pattern is:

public int Balance { get; private set; }

This means:

get
→ public

set
→ private

So outside code can read:

Console.WriteLine(account.Balance);

but cannot directly do:

account.Balance = 100000;

Inside the class, however:

Balance = 100000;

is allowed.

17. Example: Bank Account
class BankAccount
{
    public double Balance { get; private set; }

    public void Deposit(double amount)
    {
        if (amount > 0)
        {
            Balance += amount;
        }
    }
}

Usage:

BankAccount account = new BankAccount();

account.Deposit(500);

Console.WriteLine(account.Balance);

But:

account.Balance = -1000;

is not allowed from outside.

This is a practical use of encapsulation.

18. Property With Validation

Properties become especially useful when we need rules.

Example:

class Student
{
    private int age;

    public int Age
    {
        get
        {
            return age;
        }

        set
        {
            if (value >= 0 && value <= 150)
            {
                age = value;
            }
        }
    }
}

Now:

student.Age = 22;

works.

But:

student.Age = -10;

does not update the field.

And:

student.Age = 500;

also does not update it.

19. Property Can Contain Complex Logic

A property doesn't have to simply return or assign a field.

Example:

class Employee
{
    private double salary;

    public double Salary
    {
        get
        {
            return salary;
        }

        set
        {
            if (value >= 0)
            {
                salary = value;
            }
        }
    }
}

The setter enforces a business rule:

salary cannot be negative

This is one reason properties are powerful.

20. Expression-Bodied Property

If a property only calculates and returns something, we can use:

public int AgeInMonths => Age * 12;

Example:

class Student
{
    public int Age { get; set; }

    public int AgeInMonths => Age * 12;
}

Usage:

Student student = new Student();

student.Age = 22;

Console.WriteLine(student.AgeInMonths);

Output:

264

This property is calculated from another value.

21. Calculated Properties

A calculated property doesn't necessarily store its own value.

Example:

class Rectangle
{
    public double Width { get; set; }
    public double Height { get; set; }

    public double Area => Width * Height;
}

Usage:

Rectangle rectangle = new Rectangle();

rectangle.Width = 10;
rectangle.Height = 5;

Console.WriteLine(rectangle.Area);

Output:

50

Conceptually:

Width
  ↓
Height
  ↓
Area
  ↓
calculated when accessed
22. Property Can Be Write-Only

C# technically allows a property with only a setter:

public string Password
{
    set
    {
        // process value
    }
}

But write-only properties are uncommon and usually not the preferred design.

Most properties are:

get + set

or:

get only
23. init Accessor

Modern C# also provides:

init

Example:

class Student
{
    public string Name { get; init; }
    public int Age { get; init; }
}

Now values can be assigned during object initialization:

Student student = new Student
{
    Name = "Hariom",
    Age = 22
};

But after initialization:

student.Name = "Aman";

is not allowed.

Mental model:

set
→ can assign after object creation

init
→ can assign during initialization only
24. set vs init

Compare:

public string Name { get; set; }

and:

public string Name { get; init; }

With set:

Student student = new Student();

student.Name = "Hariom";
student.Name = "Aman";

Both assignments are allowed.

With init:

Student student = new Student
{
    Name = "Hariom"
};

After initialization:

student.Name = "Aman"; // Error
25. Property Initializer

You can give a property a default value:

class Student
{
    public string Name { get; set; } = "Unknown";
    public int Age { get; set; } = 0;
}

Then:

Student student = new Student();

Console.WriteLine(student.Name);

Output:

Unknown
26. Property Naming Convention

Properties normally use PascalCase.

Good:

public string Name { get; set; }
public int Age { get; set; }
public double Salary { get; set; }

Fields commonly use a different convention depending on the project's style, often:

private string name;

or:

private string _name;

The important thing is consistency.

27. Why Properties Support Encapsulation

Suppose we have:

private int age;

public int Age
{
    get
    {
        return age;
    }

    set
    {
        if (value >= 0)
        {
            age = value;
        }
    }
}

Outside code doesn't directly access:

age

Instead it interacts through:

Age property

So:

External code
      ↓
   Property
      ↓
   Field/state

This gives the class control.

28. Property Is Not Just "A Fancy Field"

This is a very important concept.

A property:

public int Age { get; set; }

is not conceptually the same thing as:

public int age;

A property represents an access contract.

It says:

This type exposes a value called Age, and here is how callers can read and/or assign it.

That access can later contain logic without changing how callers use:

student.Age
29. Example: Start Simple, Add Logic Later

Initially:

class Student
{
    public int Age { get; set; }
}

Usage:

student.Age = 22;

Later, we may need validation:

class Student
{
    private int age;

    public int Age
    {
        get => age;

        set
        {
            if (value >= 0 && value <= 150)
            {
                age = value;
            }
        }
    }
}

The caller still writes:

student.Age = 22;

The external interface remains conceptually the same.

This is a major benefit of properties.

30. Accessor Accessibility

You can restrict an individual accessor.

Example:

public int Balance
{
    get;
    private set;
}

The property itself is public.

But:

get → public
set → private

Another example:

public int Id
{
    get;
    private set;
}

This pattern is extremely common in real C# applications.

31. Property With Explicit Backing Field

Example:

class Product
{
    private double price;

    public double Price
    {
        get
        {
            return price;
        }

        set
        {
            if (value >= 0)
            {
                price = value;
            }
        }
    }
}

The flow:

product.Price = 500
       ↓
setter
       ↓
validation
       ↓
price = 500

Reading:

product.Price
       ↓
getter
       ↓
return price
32. Auto-Property vs Full Property
Auto-property
public string Name { get; set; }

Use when no custom logic is required.

Full property
private string name;

public string Name
{
    get
    {
        return name;
    }

    set
    {
        // custom logic
        name = value;
    }
}

Use when you need:

validation

calculations
side effects
special access behavior
33. Property With Transformation

A property can transform input.

Example:

class User
{
    private string username;

    public string Username
    {
        get
        {
            return username;
        }

        set
        {
            username = value.Trim().ToLower();
        }
    }
}

If:

user.Username = "  HARIOM  ";

the stored value becomes conceptually:

hariom

The property controls how data enters the object.

34. Getter Can Also Contain Logic

Example:

class Employee
{
    public double Salary { get; set; }

    public double AnnualSalary
    {
        get
        {
            return Salary * 12;
        }
    }
}

Usage:

Employee employee = new Employee();

Output:

600000

AnnualSalary is a calculated property.

35. Property Access Is Syntax

When you write:

student.Name

you don't need to know whether internally Name is:

a stored value

or:

calculated

or:

validated

or:

computed from other fields

The caller sees a consistent access syntax.

This abstraction is one of the major benefits of properties.

36. Field + Property Relationship

A common pattern:

class Student
{
    private string name;

    public string Name
    {
        get => name;
        set => name = value;
    }
}

Conceptually:

External code
      ↓
     Name
   property
      ↓
     name
  backing field

But with an auto-property:

public string Name { get; set; }

the compiler manages the backing storage for you.

37. Don't Create a Field Just Because You Have a Property

This is unnecessary:

class Student
{
    private string name;

    public string Name { get; set; }
}

Here the name field isn't connected to the property.

If you don't need custom behavior, simply use:

class Student
{
    public string Name { get; set; }
}

If you need custom behavior, explicitly connect the backing field:

private string name;

public string Name
{
    get => name;
    set => name = value;
}
38. Practical Example — Product
class Product
{
    public string Name { get; set; }

    public double Price { get; private set; }

    public Product(string name, double price)
    {
        Name = name;

        if (price >= 0)
        {
            Price = price;
        }
    }

    public void ChangePrice(double newPrice)
    {
        if (newPrice >= 0)
        {
            Price = newPrice;
        }
    }
}

Usage:

Product product = new Product("Laptop", 50000);

Console.WriteLine(product.Name);
Console.WriteLine(product.Price);

product.ChangePrice(55000);

Notice:

Name
→ public get + set

Price
→ public get
→ private set

External code can't directly modify Price.

39. Properties and Encapsulation

The relationship is:

Private field
      ↓
Property
      ↓
Controlled access
      ↓
Encapsulation

Properties are one of the main tools used to implement encapsulation in C#.

But remember:

Property and encapsulation are not synonyms.

Encapsulation is the broader design principle.

A property is a language feature used to expose controlled access.

40. Property vs Method

Sometimes beginners ask:

Why not just use methods?

You could write:

student.GetName();
student.SetName("Hariom");

instead of:

student.Name;
student.Name = "Hariom";

Properties are useful when something conceptually behaves like a value/attribute.

Methods are generally better for an action/operation.

Think:

Name
Age
Salary
Balance
Area

often make sense as properties.

While:

Study()
Deposit()
Calculate()
SendEmail()
Save()

are naturally methods.

41. Property or Method?

Good property:

public string Name { get; set; }

Good method:

public void Deposit(double amount)
{
}

Why?

Name
→ describes state

Deposit()
→ performs an action

This isn't an absolute rule, but it is a strong design guideline.

42. Important Mental Model

When you see:

student.Name = "Hariom";

think:

Assignment
     ↓
Property setter
     ↓
validation / logic
     ↓
stored state

When you see:

Console.WriteLine(student.Name);

think:

Property getter
     ↓
read state / calculate value
     ↓
return value

44. Key Differences
Concept	Meaning
Field	Stores member data
Property	Provides controlled access to a value
get	Reads property
set	Assigns property
value	Value supplied to setter
Auto-property	Property where compiler provides backing storage
private set	Only class can assign through setter
get only	External code can read but not normally assign
init	Assign during initialization
Backing field	Field used by an explicit property
45. Common Mistakes
Mistake 1

Thinking this:

public int Age { get; set; }

is a field.

It is a property.

Mistake 2

Thinking get means "constructor".

No.

get
→ read

set
→ write
Mistake 3

Using public fields everywhere:

public int age;

Prefer properties when exposing object data as part of a public API.

Mistake 4

Creating an unnecessary backing field:

private string name;

public string Name { get; set; }

If you need no custom logic, remove the field.

Mistake 5

Confusing:

public int Age { get; }

with:

public int Age { get; set; }

The first doesn't expose a public setter.
