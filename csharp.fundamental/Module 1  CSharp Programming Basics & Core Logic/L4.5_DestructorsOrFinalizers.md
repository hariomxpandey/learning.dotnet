Lesson 25 — Destructors / Finalizers in C#

Module: 1 — C# Programming Basics & Core Logic
Section: 1.4 Core Object-Oriented Programming
Prerequisite: Constructors, Classes, Objects, Encapsulation

1. First Important Correction

In C#, what beginners often call a destructor is technically a finalizer.

You may see syntax like:

class Student
{
    ~Student()
    {
        // cleanup
    }
}

It looks like a destructor from languages such as C++, but C# handles it very differently.

So remember:

C# syntax:
~ClassName()
     ↓
Finalizer

For this lesson, we'll understand both terms, but technically:

C# has finalizers, not deterministic destructors like C++.

2. Constructor vs Finalizer

We just studied constructors.

Constructor
public Student()
{
}

Runs as part of object creation.

new Student()
     ↓
constructor
     ↓
object initialized
Finalizer
~Student()
{
}

Runs when the Garbage Collector finalizes an object.

object becomes unreachable
        ↓
Garbage Collector
        ↓
finalization
        ↓
finalizer may execute

The timing is fundamentally different.

3. Basic Finalizer Syntax
class Student
{
    ~Student()
    {
        Console.WriteLine("Finalizer called");
    }
}

Notice:

~Student()

The name matches the class, but there is a ~.

There is also:

no return type
no parameters
only one finalizer can be declared for a class
it cannot be called directly
4. You Cannot Call a Finalizer Yourself

This is not valid:

student.~Student();

You don't explicitly invoke a finalizer.

The .NET runtime and Garbage Collector determine when finalization occurs.

This is very different from:

student.Dispose();

which is an explicit method call.

5. What Is Garbage Collection?

C# runs on .NET, which provides a Garbage Collector (GC).

The GC automatically manages memory for managed objects.

Suppose:

Student student = new Student();

An object exists.

Later:

student = null;

assuming there are no other references to that object, the object may become unreachable.

student
   ↓
null

Student object
   ↓
no reachable reference

The object becomes eligible for garbage collection.

6. Important: Eligible Does Not Mean Immediately Deleted

This is one of the most important concepts.

When an object becomes unreachable:

unreachable
     ≠
immediately destroyed

Instead:

Object becomes unreachable
          ↓
eligible for GC
          ↓
GC eventually runs
          ↓
memory can be reclaimed

You do not know exactly when this will happen.

7. Where Does the Finalizer Come In?

If a class has a finalizer:

class ResourceHolder
{
    ~ResourceHolder()
    {
        Console.WriteLine("Finalizer");
    }
}

the object participates in finalization.

Conceptually:

Object created
     ↓
Object becomes unreachable
     ↓
GC identifies it
     ↓
Finalization process
     ↓
Finalizer executes
     ↓
Object can later be reclaimed

There is extra runtime machinery involved for finalizable objects.

8. Finalizers Are Non-Deterministic

Non-deterministic means you don't control exactly when the finalizer executes.

Example:

ResourceHolder holder = new ResourceHolder();

holder = null;

You cannot say:

"Finalizer will execute right here."

It may happen later.

Therefore, this is dangerous:

~ResourceHolder()
{
    SaveImportantData();
}

if your program depends on that operation happening at a particular time.

9. Why Finalizers Exist

Finalizers exist mainly for a special situation:

A managed object owns an unmanaged resource and needs a last-resort cleanup mechanism.

Examples of unmanaged resources can include:

native OS handles
native memory
certain operating-system resources

These resources aren't managed by the .NET GC in the same way ordinary managed objects are.

10. Managed vs Unmanaged Resources

This distinction is critical.

Managed resource

Examples:

string
List<T>
Dictionary<TKey,TValue>
another .NET object

The GC manages the memory associated with managed objects.

Unmanaged resource

Examples can include:

OS handles
native resources
memory allocated outside the managed heap

The GC doesn't automatically know the correct domain-specific cleanup operation for those resources.

That's where explicit resource-management patterns come in.

11. Don't Use Finalizers for Normal Memory Cleanup

Suppose:

class Student
{
    private string name;

    ~Student()
    {
        // unnecessary
    }
}

There is generally no reason to add a finalizer just because the object contains:

string
int
double
List<T>

The GC already handles ordinary managed memory.

Don't think:

Every class
    ↓
needs finalizer

That's incorrect.

12. Finalizer Is Not Dispose()

This distinction is extremely important.

Finalizer:

~ResourceHolder()
{
}

is runtime-controlled.

Dispose():

public void Dispose()
{
}

is normally explicitly called by your code or by a using construct.

Think:

Finalizer
→ automatic
→ non-deterministic

Dispose
→ explicit
→ deterministic
13. What Does Deterministic Cleanup Mean?

Suppose you open a resource:

file
database connection
network resource
OS handle

You usually want:

Use resource
    ↓
finish
    ↓
release immediately

That's deterministic cleanup.

With Dispose():

resource.Dispose();

you explicitly tell the resource:

"I'm finished with you; release what you own."

You don't wait for the GC.

14. IDisposable

.NET provides an interface specifically for deterministic resource cleanup:

IDisposable

Basic example:

class ResourceHolder : IDisposable
{
    public void Dispose()
    {
        // release resources
    }
}

Now:

ResourceHolder holder = new ResourceHolder();

holder.Dispose();

The cleanup is explicit.

15. Why IDisposable Exists

Imagine a class owns something that must be released quickly.

You don't want:

Wait for GC
    ↓
maybe later
    ↓
resource finally released

Instead:

Use resource
    ↓
Dispose()
    ↓
resource released

This is why IDisposable is central to .NET resource management.

16. using and IDisposable

C# provides a convenient way to ensure Dispose() is called.

Example:

using (ResourceHolder holder = new ResourceHolder())
{
    // use holder
}

When execution leaves the using block, disposal happens.

Conceptually:

using
  ↓
create resource
  ↓
use resource
  ↓
leave block
  ↓
Dispose()

This is much more predictable than waiting for a finalizer.

17. Modern using Syntax

You can also write:

using ResourceHolder holder = new ResourceHolder();

holder.Use();

The variable is disposed automatically when the relevant scope ends.

This is called a using declaration.

The exact scope matters, but the key idea is:

scope ends
    ↓
Dispose()
18. Simple IDisposable Example
class FileResource : IDisposable
{
    public void Use()
    {
        Console.WriteLine("Using resource");
    }

    public void Dispose()
    {
        Console.WriteLine("Resource released");
    }
}

Usage:

using (FileResource resource = new FileResource())
{
    resource.Use();
}

Conceptually:

Resource created
       ↓
Use()
       ↓
scope ends
       ↓
Dispose()
19. Finalizer + IDisposable

A class that owns an unmanaged resource may sometimes implement both.

Conceptually:

class ResourceHolder : IDisposable
{
    public void Dispose()
    {
        // release unmanaged resource
        GC.SuppressFinalize(this);
    }

    ~ResourceHolder()
    {
        // fallback cleanup
    }
}

The important idea is:

Dispose()
→ primary cleanup path

Finalizer
→ safety-net/fallback path
20. Why GC.SuppressFinalize(this)?

Suppose:

public void Dispose()
{
    ReleaseResource();

    GC.SuppressFinalize(this);
}

If Dispose() has already performed the required cleanup, there is usually no need for the finalizer to run later.

So:

Dispose()
    ↓
cleanup complete
    ↓
Suppress finalization
    ↓
avoid unnecessary finalization

GC.SuppressFinalize(this) tells the GC that the object does not need finalization.

21. Standard Dispose Pattern — Basic Version

A simplified pattern looks like:

class ResourceHolder : IDisposable
{
    private bool disposed;

    public void Dispose()
    {
        Dispose(true);
        GC.SuppressFinalize(this);
    }

    protected virtual void Dispose(bool disposing)
    {
        if (disposed)
            return;

        if (disposing)
        {
            // release managed resources
        }

        // release unmanaged resources

        disposed = true;
    }

    ~ResourceHolder()
    {
        Dispose(false);
    }
}

Don't memorize this yet.

Understand the idea first.

22. Why Two Cleanup Paths?

There are two possible scenarios.

Scenario 1 — User explicitly disposes
Dispose()
   ↓
Dispose(true)
   ↓
cleanup
   ↓
SuppressFinalize
Scenario 2 — User forgets to dispose
object becomes unreachable
        ↓
GC
        ↓
finalizer
        ↓
Dispose(false)
        ↓
unmanaged cleanup

The finalizer is a backup.

23. Why Dispose(true) and Dispose(false)?

The boolean tells the cleanup method whether disposal was initiated explicitly.

true
→ explicit Dispose()

false
→ finalizer

Why does this matter?

Because when the finalizer runs, you should not generally assume that other managed objects are still safely available for cleanup.

So finalizer cleanup focuses on unmanaged resources.

24. Finalizer Should Be a Last Resort

A good mental model:

Preferred
   ↓
Dispose()
   ↓
using
   ↓
deterministic cleanup

Fallback
   ↓
Finalizer
   ↓
last chance for unmanaged cleanup

Don't design ordinary classes around finalizers.

25. Why Finalizers Have a Cost

Objects with finalizers require additional GC handling.

A simplified view:

Normal object
     ↓
GC
     ↓
reclaim memory

Finalizable object:

object
  ↓
GC detects it
  ↓
finalization processing
  ↓
finalizer runs
  ↓
later reclamation

This adds overhead and can delay memory reclamation.

Therefore:

Don't add a finalizer unless you have a real unmanaged-resource-management reason.

26. Finalizer Does Not Guarantee Immediate Cleanup

Suppose:

class ResourceHolder
{
    ~ResourceHolder()
    {
        Console.WriteLine("Cleanup");
    }
}

You do:

ResourceHolder holder = new ResourceHolder();

holder = null;

You cannot assume:

"Cleanup" immediately prints.

The GC decides when collection/finalization occurs.

27. GC.Collect() Is Not Normal Cleanup

You may see:

GC.Collect();

This explicitly requests a garbage collection.

But don't use it as a normal replacement for Dispose().

Bad mindset:

I have a resource
     ↓
GC.Collect()
     ↓
problem solved

Instead:

I own a disposable resource
     ↓
Dispose()

GC is for managed memory management, not a general-purpose resource-release API.

28. GC.Collect() Still Doesn't Mean "Finalizer Finished"

Even if you force collection, finalization can involve additional runtime steps.

So don't build application logic around assumptions like:

GC.Collect()
→ all finalizers have already completed

The runtime provides separate mechanisms such as GC.WaitForPendingFinalizers() for specialized scenarios, but manually forcing GC/finalization is generally not how ordinary resource management should be designed.

29. Finalizer vs Dispose
Feature	Finalizer	Dispose()
Called by	GC/runtime	Your code / using
Timing	Non-deterministic	Deterministic
Directly callable?	No	Yes
Main purpose	Last-resort unmanaged cleanup	Explicit resource cleanup
Common for ordinary classes?	No	Only when needed
Performance overhead	Yes	Normal method call
IDisposable required?	No	Usually yes

The most important row:

Finalizer → don't control exact timing

Dispose → control when cleanup happens
30. Constructor vs Finalizer
Constructor	Finalizer
ClassName()	~ClassName()
Object initialization	Last-resort cleanup
Runs during object creation	Runs during GC finalization
Deterministic timing	Non-deterministic
Can have parameters	Cannot have parameters
Can be overloaded	Cannot be overloaded
Common	Rare
31. Finalizers Cannot Have Parameters

This is invalid:

~Student(int id)
{
}

A finalizer must have this form:

~Student()
{
}

No parameters.

32. Finalizers Cannot Be Inherited Normally

A finalizer is associated with the class that declares it.

You don't write:

~BaseClass()

inside a derived class to somehow "override" it.

Finalization has special runtime semantics.

This is different from normal virtual method overriding.

33. Finalizers Cannot Be Called Directly

Again:

~Student()
{
}

doesn't mean you can write:

student.~Student();

No.

The runtime controls finalization.

34. Finalizers Are Not Guaranteed to Run in Every Situation

Do not use a finalizer as if it were guaranteed application shutdown logic.

For example, abrupt process termination can prevent normal finalization behavior.

Therefore:

Critical cleanup
    ↓
Do not rely only on finalizer

Use deterministic cleanup where required.

35. Example — Resource Ownership

Imagine:

class NativeResourceHolder
{
    // Imagine this stores an unmanaged OS handle.
}

If the object owns an unmanaged resource, you need a strategy to release it.

Conceptually:

Native handle acquired
       ↓
object owns handle
       ↓
Dispose()
       ↓
release handle

If the programmer fails to dispose:

object unreachable
       ↓
finalizer
       ↓
last-resort release

That is the reason finalizers exist.

36. Ownership Is the Key Idea

Ask:

"Does my class own a resource that needs explicit release?"

If the answer is:

No

you generally don't need a finalizer.

If:

Yes — unmanaged resource

then resource-management patterns such as IDisposable become important.

Mental model:

Class owns resource
       ↓
Class responsible for cleanup
       ↓
IDisposable
       ↓
Dispose()
       ↓
optional finalizer as fallback
37. Don't Dispose Everything

A common misunderstanding is:

"If I use an object, I should call Dispose()."

No.

Only objects implementing IDisposable have the Dispose() contract.

For example, ordinary classes like:

class Student
{
    public string Name { get; set; }
}

do not need:

student.Dispose();

There is nothing requiring deterministic resource cleanup.

38. Managed Objects Can Own Disposable Objects

This is an important real-world situation.

Suppose:

class ReportService : IDisposable
{
    private SomeDisposableResource resource;

    public void Dispose()
    {
        resource.Dispose();
    }
}

Even though resource is itself a managed object, it may represent something that requires deterministic cleanup.

So the important question isn't simply:

"Is this object managed?"

Instead:

"Does this object own resources requiring deterministic release?"
39. using Is About Dispose, Not Finalizer

When you write:

using (var resource = new Resource())
{
    resource.Use();
}

the key guarantee is:

scope exit
   ↓
Dispose()

It does not mean:

scope exit
   ↓
finalizer immediately

These are completely different mechanisms.

40. Practical Example
class FileManager : IDisposable
{
    private bool disposed;

    public void Open()
    {
        Console.WriteLine("Resource opened");
    }

    public void Dispose()
    {
        if (disposed)
            return;

        Console.WriteLine("Resource released");

        disposed = true;
        GC.SuppressFinalize(this);
    }

    ~FileManager()
    {
        Console.WriteLine("Finalizer");
    }
}

Usage:

using (FileManager manager = new FileManager())
{
    manager.Open();
}

The intended flow:

new FileManager()
       ↓
Open()
       ↓
leave using
       ↓
Dispose()
       ↓
SuppressFinalize()

Because explicit disposal happened, finalization doesn't need to be used as the fallback.

41. Important Design Rule

If your class implements IDisposable:

class ResourceHolder : IDisposable

then users should be able to understand:

"After I'm finished with this object,
I should dispose it."

That's why the using pattern is so important.

42. Finalizer Is a Safety Net, Not a Primary API

Think about a car's emergency brake.

You don't normally drive using:

emergency brake

You use:

normal brake

Similarly:

Normal cleanup
→ Dispose()

Fallback cleanup
→ Finalizer

This is a useful mental model.

43. Common Mistakes
Mistake 1

Thinking every class needs a finalizer.

Wrong

Finalizers are specialized.

Mistake 2

Thinking finalizer runs immediately when a reference becomes null.

Wrong

The object becomes eligible for collection; timing is controlled by the GC.

Mistake 3

Using a finalizer instead of Dispose().

Wrong for deterministic cleanup

Use Dispose() when the resource needs timely release.

Mistake 4

Calling GC.Collect() to clean resources.

Wrong design

Use Dispose() / using for deterministic resource cleanup.

Mistake 5

Thinking:

finalizer = C++ destructor

Not exactly.

C# finalizers are runtime/GC-controlled.

44. The Most Important Mental Model

Remember this:

             OBJECT
                │
       ┌────────┴────────┐
       │                 │
    Managed          Unmanaged
    resources         resources
       │                 │
       ↓                 ↓
      GC             explicit cleanup
                         │
                         ↓
                    IDisposable
                         │
                         ↓
                      Dispose()
                         │
                         ↓
                   Finalizer
                   (fallback)

This is the big picture.

45. Constructor → Finalizer Lifecycle

At a high level:

new Object()
    ↓
Constructor
    ↓
Object in use
    ↓
No reachable references
    ↓
Eligible for GC
    ↓
If finalizable → finalization processing
    ↓
Finalizer
    ↓

Important:

No reachable references

does not mean:

finalizer immediately runs
46. What You Should Use in Real C# Code

For normal classes:

class Student
{
}

No finalizer.

For disposable resources:

class ResourceHolder : IDisposable
{
    public void Dispose()
    {
        // cleanup
    }
}

Use:

using var resource = new ResourceHolder();

For classes directly owning unmanaged resources, a finalizer may be appropriate as part of a carefully implemented resource-management pattern.

47. Finalizer vs IDisposable — Final Understanding
Finalizer
─────────

Non-deterministic
Fallback

IDisposable

So the rule to remember is:

Use Dispose() for deterministic cleanup. Treat a finalizer as a specialized safety net for unmanaged resources, not as a normal "destructor" for every class.
