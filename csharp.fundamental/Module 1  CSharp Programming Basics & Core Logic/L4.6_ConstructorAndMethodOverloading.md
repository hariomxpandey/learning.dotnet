Lesson 26 — Constructor & Method Overloading

Goal: Understand how C# chooses between multiple constructors/methods with the same name, how signatures work, and where overloading can become ambiguous.

1. First: What Is Overloading?

You already covered the basic idea of method overloading, so we won't repeat the fundamentals.

The important concept for this lesson is:

Overloading means multiple members have the same name but different parameter signatures.

Example:

void Print(int number)
{
}

void Print(string text)
{
}

void Print(int number, string text)
{
}

The name is the same:

Print

But the parameter lists are different.

Print(int)
Print(string)
Print(int, string)

C# uses the arguments supplied in the call to determine which one should execute.

2. What Is a Method Signature?

For overloading, the signature is extremely important.

Consider:

void Add(int a, int b)
{
}

void Add(double a, double b)
{
}

These can coexist because their parameter types differ:

Add(int, int)
Add(double, double)

But this is not allowed:

void Add(int a, int b)
{
}

void Add(int x, int y)
{
}

Why?

Because parameter names don't matter for overload identity.

(int a, int b)
(int x, int y)

Both are effectively:

(int, int)

So C# sees them as the same signature.

3. Return Type Is NOT Enough

This is a very important rule.

You cannot overload a method only by changing its return type.

❌ Invalid:

int GetValue()
{
    return 10;
}

string GetValue()
{
    return "Hello";
}

C# cannot use the return type to determine which method you intended.

For example:

GetValue();

Which one should execute?

There is no argument information to distinguish them.

Therefore:

Return type alone cannot create an overload.

4. Constructor Overloading

Now the important remaining part: constructor overloading.

A class can have multiple constructors.

Example:

class Student
{
    public string Name;
    public int Age;

    public Student()
    {
        Name = "Unknown";
        Age = 0;
    }

    public Student(string name)
    {
        Name = name;
        Age = 0;
    }

    public Student(string name, int age)
    {
        Name = name;
        Age = age;
    }
}

Now we can create objects in different ways.

Student s1 = new Student();

Student s2 = new Student("Hariom");

Student s3 = new Student("Hariom", 21);

C# selects the appropriate constructor based on the arguments.

5. Why Constructor Overloading Is Useful

Suppose you have:

class Product
{
    public string Name;
    public double Price;
}

You might want to allow:

No information
Product p1 = new Product();
Only name
Product p2 = new Product("Laptop");
Name + price
Product p3 = new Product("Laptop", 50000);

Instead of forcing every caller to provide every value, constructor overloading gives multiple valid ways to initialize an object.

6. Constructor Signature

Just like methods, constructors are distinguished by their parameter list.

class Employee
{
    public Employee()
    {
    }

    public Employee(string name)
    {
    }

    public Employee(string name, int age)
    {
    }
}

Their signatures are effectively:

Employee()
Employee(string)
Employee(string, int)

Therefore, all three are valid.

7. Constructor Overloading + this

One of the most useful patterns is constructor chaining.

Instead of duplicating initialization logic:

class Student
{
    public string Name;
    public int Age;

    public Student()
    {
        Name = "Unknown";
        Age = 0;
    }

    public Student(string name)
    {
        Name = name;
        Age = 0;
    }

    public Student(string name, int age)
    {
        Name = name;
        Age = age;
    }
}

We can improve it using this(...).

class Student
{
    public string Name;
    public int Age;

    public Student() : this("Unknown", 0)
    {
    }

    public Student(string name) : this(name, 0)
    {
    }

    public Student(string name, int age)
    {
        Name = name;
        Age = age;
    }
}

Now the constructors form a chain:

Student()
   ↓
Student(string, int)

Student(string)
   ↓
Student(string, int)

Only the final constructor contains the actual initialization logic.

8. Why this(...) Is Better Here

Without constructor chaining:

public Student()
{
    Name = "Unknown";
    Age = 0;
}

public Student(string name)
{
    Name = name;
    Age = 0;
}

public Student(string name, int age)
{
    Name = name;
    Age = age;
}

The same initialization logic is repeated.

This can create maintenance problems.

Suppose later you add:

public string Course;

Now multiple constructors may need modification.

With chaining:

public Student() : this("Unknown", 0)
{
}

public Student(string name) : this(name, 0)
{
}

public Student(string name, int age)
{
    Name = name;
    Age = age;
}

There is a single place where the actual initialization happens.

This follows the principle:

Don't duplicate initialization logic.

9. Constructor Overloading vs Optional Parameters

Sometimes you don't actually need multiple constructors.

For example:

class Student
{
    public string Name;
    public int Age;

    public Student(string name = "Unknown", int age = 0)
    {
        Name = name;
        Age = age;
    }
}

Now:

Student s1 = new Student();

Student s2 = new Student("Hariom");

Student s3 = new Student("Hariom", 21);

All can work.

So when should you use overloading?

Constructor overloading

Useful when different initialization paths have meaningful behavior.

public Student()
{
    // specific logic
}

public Student(string name)
{
    // different logic
}
Optional parameters

Useful when the initialization logic is fundamentally the same and only defaults differ.

public Student(string name = "Unknown", int age = 0)
{
}
10. Important: Optional Parameters Can Cause Ambiguity

Be careful when combining overloads with optional parameters.

Example:

void Print(int x)
{
}

void Print(int x, int y = 10)
{
}

Now:

Print(5);

Both methods can potentially accept the call.

Print(int)
Print(int, int = 10)

This creates an overload-resolution problem.

Lesson

Don't create overload sets where multiple methods can naturally match the same call.

11. Overload Resolution

When you write:

Print(10);

C# performs overload resolution.

Conceptually, it asks:

1. What methods have the name Print?
        ↓
2. Which parameter lists can accept the arguments?
        ↓
3. Which candidate is the best match?
        ↓
4. Call that method

Example:

void Print(int x)
{
    Console.WriteLine("int");
}

void Print(double x)
{
    Console.WriteLine("double");
}

Calling:

Print(10);

selects:

Print(int x)

because 10 is an int.

Calling:

Print(10.5);

selects:

Print(double x)

because 10.5 is a double.

12. Exact Match vs Conversion

Consider:

void Print(long x)
{
    Console.WriteLine("long");
}

void Print(double x)
{
    Console.WriteLine("double");
}

Now:

int number = 10;

Print(number);

An int can implicitly convert to both:

int → long
int → double

But C# considers the better applicable conversion according to its overload-resolution rules rather than simply treating both as equal.

The important practical lesson is:

Overload resolution considers implicit conversions, not just exact type equality.

Therefore, overloaded APIs should be designed carefully when numeric conversions are involved.

13. ref and out in Overloading

ref and out participate in method signatures.

For example:

void Process(int x)
{
}

void Process(ref int x)
{
}

These are different parameter forms.

Process(int)
Process(ref int)

So they can be overloaded.

Similarly:

void Process(int x)
{
}

void Process(out int x)
{
    x = 10;
}

These represent different parameter passing modes.

However, don't use ref/out merely to create confusing overloads.

Good API design matters more than simply finding technically valid overload combinations.

14. ref vs out Overload Detail

A subtle point:

You cannot overload a method using only ref vs out.

❌ This is not allowed:

void Test(ref int x)
{
}

void Test(out int x)
{
    x = 10;
}

Why?

Because for signature purposes, ref and out are considered the same signature shape for this purpose.

So:

Test(ref int)
Test(out int)

cannot coexist as overloads.

15. in Parameters

Modern C# also has in parameters.

Example:

void Process(in int value)
{
}

in means the argument is passed by reference but is intended to be read-only inside the method.

You should understand the distinction:

value parameter
    ↓
copy of value

ref
    ↓
read/write reference

out
    ↓
method must assign a value

in
    ↓
read-only reference

These are parameter-passing mechanisms, not simply different names.

16. Constructor Overloading With base

Constructor chaining can also move upward through inheritance.

Example:

class Person
{
    public string Name;

    public Person(string name)
    {
        Name = name;
    }
}

Derived class:

class Student : Person
{
    public int Age;

    public Student(string name, int age)
        : base(name)
    {
        Age = age;
    }
}

The chain becomes:

Student constructor
       ↓
base(name)
       ↓
Person constructor

This is different from:

this(...)

Remember:

this(...) → another constructor in the SAME class

base(...) → constructor in the BASE class

This distinction is extremely important.

17. this(...) vs base(...)
Syntax	Meaning
this(...)	Call another constructor in the same class
base(...)	Call a constructor of the base class

Example:

class Student : Person
{
    public Student()
        : this("Unknown", 0)
    {
    }

    public Student(string name, int age)
        : base(name)
    {
        Age = age;
    }

    public int Age;
}

The chain is:

Student()
   ↓ this(...)
Student(string, int)
   ↓ base(...)
Person(string)

So the complete initialization flow is:

Student()
   ↓
Student(string, int)
   ↓
Person(string)
18. Can Constructors Be static?

Yes.

C# supports a static constructor.

Example:

class Database
{
    static Database()
    {
        Console.WriteLine("Static constructor");
    }
}

But a static constructor is fundamentally different from normal constructor overloading.

A static constructor:

has no access modifier
has no parameters
cannot be called directly
runs automatically
initializes static state

Example:

class Configuration
{
    public static string AppName;

    static Configuration()
    {
        AppName = "My App";
    }
}

Then:

Console.WriteLine(Configuration.AppName);

can trigger the static initialization.

We will treat static constructors as part of deeper static/type initialization concepts rather than mixing them into normal constructor overloading.

19. Constructor Overloading and Object Creation

Consider:

class Account
{
    public string Owner;
    public decimal Balance;

    public Account()
        : this("Unknown", 0)
    {
    }

    public Account(string owner)
        : this(owner, 0)
    {
    }

    public Account(string owner, decimal balance)
    {
        Owner = owner;
        Balance = balance;
    }
}

Now:

Account a1 = new Account();

Flow:

new Account()
      ↓
Account()
      ↓
this("Unknown", 0)
      ↓
Account(string, decimal)
Account a2 = new Account("Hariom");

Flow:

new Account("Hariom")
      ↓
Account(string)
      ↓
this("Hariom", 0)
      ↓
Account(string, decimal)
Account a3 = new Account("Hariom", 5000);

Flow:

new Account("Hariom", 5000)
      ↓
Account(string, decimal)

This is the mental model you should remember.

20. A Common Mistake

Avoid writing this:

class Student
{
    public Student()
    {
        Name = "Unknown";
        Age = 0;
    }

    public Student(string name)
    {
        Name = name;
        Age = 0;
    }

    public Student(string name, int age)
    {
        Name = name;
        Age = age;
    }

    public string Name;
    public int Age;
}

It works.

But if the initialization logic becomes more complex, duplication grows.

Prefer:

class Student
{
    public string Name;
    public int Age;

    public Student()
        : this("Unknown", 0)
    {
    }

    public Student(string name)
        : this(name, 0)
    {
    }

    public Student(string name, int age)
    {
        Name = name;
        Age = age;
    }
}
21. Overloading vs Overriding

These two concepts are frequently confused.

Overloading

Same class:

void Print(int x)
{
}

void Print(string x)
{
}

Different parameters.

Compile-time concept
Overriding

Inheritance:

class Animal
{
    public virtual void Speak()
    {
    }
}

class Dog : Animal
{
    public override void Speak()
    {
    }
}

Same method signature, but derived class provides a new implementation.

Runtime polymorphism

We will study virtual, override, and new properly in Module 2 — Polymorphism, so we won't repeat that topic here.

23. Important Rules to Remember
1. Same method name + different parameter signature
   → overload

2. Return type alone cannot overload a method

3. Parameter names do not distinguish overloads

4. ref and out cannot differ only by ref/out

5. this(...)
   → constructor in same class

6. base(...)
   → constructor in base class

7. Constructor overloading gives multiple object initialization paths

8. Constructor chaining avoids duplicated initialization logic

9. Optional parameters can sometimes make overloads ambiguous

10. Overload resolution happens at compile time
