Encapsulation & Access Modifiers

Module: 1 — C# Programming Basics & Core Logic
Section: 1.4 Core Object-Oriented Programming
Prerequisite: Fields + Properties

1. What Is Encapsulation?

Encapsulation means keeping an object's internal data and implementation details protected, and allowing access through a controlled interface.

Simple mental model:

Object
│
├── Internal data
│   └── protected
│
└── Public interface
    ├── properties
    └── methods

The outside world should not necessarily be able to directly manipulate the object's internal state.

2. The Problem Without Encapsulation

Suppose we create a bank account:

class BankAccount
{
    public double Balance;
}

Now anyone can do:

BankAccount account = new BankAccount();

account.Balance = 50000;
account.Balance = -100000;

The class has no control over its own state.

This is dangerous because the object can enter an invalid state.

External code
     ↓
directly changes
     ↓
object data
     ↓
invalid state possible
3. Encapsulation Solves This

Instead:

class BankAccount
{
    private double balance;

    public void Deposit(double amount)
    {
        if (amount > 0)
        {
            balance += amount;
        }
    }
}

Now:

account.Deposit(5000);

is allowed.

But:

account.balance = -5000;

is not allowed.

The object controls how its state changes.

External code
     ↓
 Deposit()
     ↓
 validation
     ↓
 balance
4. Encapsulation Is More Than private

A common beginner misunderstanding is:

"Encapsulation means making fields private."

private is an important tool for encapsulation, but encapsulation is the broader design idea.

Encapsulation means:

Hide internal implementation
        +
Expose controlled operations

For example:

class BankAccount
{
    private double balance;

    public double Balance
    {
        get { return balance; }
    }

    public void Deposit(double amount)
    {
        if (amount > 0)
        {
            balance += amount;
        }
    }
}

Here:

balance is hidden.
Balance provides read access.
Deposit() controls modification.

That is encapsulation.

5. Access Modifiers

C# provides access modifiers to control who can access a type or member.

The important ones are:

public
private
protected
internal
protected internal
private protected

For your current level, first master these four:

public
private
protected
internal

Then understand the combinations.

6. public

public means the member is accessible wherever the containing type is accessible.

Example:

class Student
{
    public string Name;
}

Outside the class:

Student student = new Student();

student.Name = "Hariom";

Console.WriteLine(student.Name);

Allowed.

Mental model:

public
  ↓
widely accessible
7. private

private means the member is accessible only within its containing type.

Example:

class Student
{
    private int age;

    public void SetAge(int value)
    {
        age = value;
    }
}

Inside the class:

age = 22;

Allowed.

Outside:

Student student = new Student();

student.age = 22;

Not allowed.

private
   ↓
only containing type
8. public vs private

Compare:

class Student
{
    public string Name;
    private int age;
}

Outside:

student.Name = "Hariom";  // Allowed

student.age = 22;         // Error

So:

Name
→ public
→ outside code can access

age
→ private
→ outside code cannot directly access
9. Why private Is Important

Suppose:

class BankAccount
{
    private double balance;
}

Now the class has ownership over the data.

External code cannot arbitrarily change:

balance

Instead, the class can decide:

public void Deposit(double amount)
{
    if (amount <= 0)
        return;

    balance += amount;
}

This gives the class control over its invariants.

10. What Is an Invariant?

An invariant is a condition that should remain true for an object.

For example:

Bank account balance should not become invalid.

Another example:

Student age should not be negative.

Another:

Product price should not be negative.

Encapsulation helps protect these rules.

Encapsulation
      ↓
Control access
      ↓
Protect invariants
      ↓
Keep object valid

This is a very important OOP idea.

11. protected

protected is mainly related to inheritance.

A protected member is accessible from:

The containing class.
Derived classes.

Example:

class Animal
{
    protected string name;
}

Derived class:

class Dog : Animal
{
    public void ShowName()
    {
        Console.WriteLine(name);
    }
}

Dog can access name because Dog derives from Animal.

12. protected vs private

Consider:

class Animal
{
    private string privateName;
    protected string protectedName;
}

Derived class:

class Dog : Animal
{
    public void Test()
    {
        // privateName = "Dog";   // Error
        protectedName = "Dog";     // Allowed
    }
}

So:

private
→ containing class only

protected
→ containing class + derived classes
13. Why protected Exists

Imagine a base class provides common internal state:

class Vehicle
{
    protected int speed;
}

A derived class:

class Car : Vehicle
{
    public void Accelerate()
    {
        speed += 10;
    }
}

The base class shares selected internal functionality with derived classes.

But unrelated outside code still cannot directly access:

car.speed;
14. internal

internal means accessible within the same assembly.

Example:

internal class Student
{
    internal string Name;
}

Code within the same assembly can access it.

Code from another assembly generally cannot access it unless additional mechanisms such as InternalsVisibleTo are used.

Mental model:

internal
   ↓
same assembly
15. What Is an Assembly?

You will encounter this concept frequently in real C# development.

An assembly is a compiled .NET unit such as:

.dll
.exe

For example:

MyApplication.exe
MyLibrary.dll

internal is primarily about access within the same assembly.

16. Four Core Access Modifiers

For now, memorize this table:

Modifier	Accessible from
public	Anywhere the containing type is accessible
private	Containing type
protected	Containing type + derived types
internal	Same assembly

Mental model:

public
→ everyone with access

private
→ me

protected
→ me + my children

internal
→ my assembly
17. protected internal

Now combine:

protected internal

This means access is allowed when either condition is satisfied:

same assembly
OR
derived type

Example:

class Parent
{
    protected internal int value;
}

This is broader than simply protected or internal individually.

Mental model:

protected internal
       ↓
   protected
      OR
   internal
18. private protected

This is more restrictive.

private protected

means the member is accessible from:

the containing type
+
derived types within the same assembly

Mental model:

private protected
       ↓
private
   +
protected
within same assembly

It is useful when a base class wants to expose something to its derived classes, but only within the same assembly.

19. protected internal vs private protected

This is a common interview question.

protected internal
same assembly
OR
derived class
private protected
same assembly
AND
derived class

The difference is essentially:

protected internal → OR

private protected → AND
20. Access Modifier Hierarchy

Think about accessibility roughly like this:

Most accessible
      ↓
public
      ↓
protected internal
      ↓
internal / protected
      ↓
private protected
      ↓
private
      ↓
Least accessible

Do not treat this as a universal mathematical ordering in every language rule; use the actual access definitions when precision matters.

The important thing is understanding who can access what.

21. Default Access for Class Members

If you don't specify an access modifier for a class member, its default accessibility is generally:

private

Example:

class Student
{
    string name;
}

is effectively:

class Student
{
    private string name;
}

for that field.

This is important.

22. Default Access for Top-Level Types

For a top-level class, if no modifier is specified:

class Student
{
}

the default accessibility is:

internal

So:

class Student
{
}

is effectively:

internal class Student
{
}

This differs from members inside a class.

Remember:

Top-level class
→ internal by default

Class member
→ private by default
23. Encapsulation With Fields

Bad design:

class Employee
{
    public double salary;
}

External code:

employee.salary = -50000;

Better:

class Employee
{
    private double salary;

    public double Salary
    {
        get
        {
            return salary;
        }

        private set
        {
            salary = value;
        }
    }

    public void IncreaseSalary(double amount)
    {
        if (amount > 0)
        {
            Salary += amount;
        }
    }
}

Now the class controls modifications.

24. Encapsulation With Properties

A common pattern is:

class Student
{
    private int age;

    public int Age
    {
        get
        {
            return age;
        }

        set
        {
            if (value >= 0)
            {
                age = value;
            }
        }
    }
}

Outside:

student.Age = 22;

Inside:

Age setter
   ↓
validation
   ↓
age field

The field is hidden.

The property is the controlled interface.

25. Encapsulation With private set

Often we don't even need a full backing field.

class BankAccount
{
    public double Balance { get; private set; }

    public void Deposit(double amount)
    {
        if (amount > 0)
        {
            Balance += amount;
        }
    }
}

Outside:

Console.WriteLine(account.Balance);

Allowed.

But:

account.Balance = 1000;

Not allowed.

Inside:

Balance += amount;

Allowed.

26. Read Access vs Write Access

Think about access modifiers at the property-accessor level:

public double Balance { get; private set; }

This creates two different permissions:

get
 ↓
public

set
 ↓
private

Therefore:

Outside
→ read

Inside class
→ read + write

This is excellent for encapsulation.

27. Encapsulation Does Not Mean "No Access"

This is another common misconception.

Bad understanding:

Encapsulation
→ hide everything

Correct:

Encapsulation
→ hide what should be hidden
→ expose what should be exposed
→ control how it is accessed

For example, a bank account should expose:

Balance → read
Deposit() → allowed operation
Withdraw() → allowed operation

But shouldn't expose unrestricted:

balance field → direct modification
28. Example: Bank Account
class BankAccount
{
    private double balance;

    public double Balance
    {
        get
        {
            return balance;
        }
    }

    public void Deposit(double amount)
    {
        if (amount > 0)
        {
            balance += amount;
        }
    }

    public bool Withdraw(double amount)
    {
        if (amount <= 0)
            return false;

        if (amount > balance)
            return false;

        balance -= amount;
        return true;
    }
}

Usage:

BankAccount account = new BankAccount();

account.Deposit(1000);

Console.WriteLine(account.Balance);

account.Withdraw(300);

Console.WriteLine(account.Balance);

The outside world doesn't directly manipulate balance.

29. Why This Design Is Better

Without encapsulation:

External code
      ↓
balance = anything
      ↓
object can become invalid

With encapsulation:

External code
      ↓
Deposit / Withdraw
      ↓
validation
      ↓
balance

The object protects itself.

30. Encapsulation and Abstraction Are Different

Don't mix these concepts.

Encapsulation

Focuses on:

How data and implementation are packaged
and access is controlled.
Abstraction

Focuses on:

What details should be exposed
and what complexity should be hidden.

Example:

BankAccount
│
├── private balance
│
├── Deposit()
└── Withdraw()

Encapsulation controls access to balance.

Abstraction lets the caller think in terms of:

Deposit money
Withdraw money

without needing to know every internal detail.

We'll study abstraction later in Module 2.

31. Access Modifiers Are About Boundaries

Think of a class as a boundary:

              CLASS
┌──────────────────────────────┐
│                              │
│ private data                 │
│ private methods              │
│                              │
│ protected members            │
│                              │
│ public interface             │
│                              │
└──────────────────────────────┘
                ↑
                │
          outside world

The access modifiers determine what can cross that boundary.

32. A Real Design Pattern

A well-designed class often looks like:

class User
{
    private string password;

    public string Username { get; private set; }

    public void ChangePassword(string newPassword)
    {
        // validation
        password = newPassword;
    }
}

Notice:

password
→ private

Username
→ publicly readable

Username setter
→ private

ChangePassword()
→ public controlled operation

The class exposes capabilities, not unrestricted internal state.

33. Public Fields vs Public Properties

Prefer:

public string Name { get; set; }

over:

public string name;

when exposing object state as part of a class's API.

Why?

Because properties allow you to later introduce:

validation
calculation
logging
access restrictions
transformation

without changing the basic access syntax.

34. Access Modifiers on Methods

Access modifiers aren't only for fields.

Example:

class Student
{
    private void CalculateInternalMarks()
    {
    }

    public void DisplayResult()
    {
        CalculateInternalMarks();
    }
}

Outside code can call:

student.DisplayResult();

but cannot call:

student.CalculateInternalMarks();

So encapsulation can protect:

data
+
behavior

not just data.

35. Private Methods

Private methods are useful for implementation details.

Example:

class Order
{
    public void PlaceOrder()
    {
        ValidateOrder();
        SaveOrder();
    }

    private void ValidateOrder()
    {
        // internal logic
    }

    private void SaveOrder()
    {
        // internal logic
    }
}

Outside code only needs:

order.PlaceOrder();

It doesn't need direct access to internal helper methods.

36. Good Encapsulation Example
class Employee
{
    private double salary;

    public string Name { get; private set; }

    public double Salary
    {
        get
        {
            return salary;
        }
    }

    public Employee(string name, double salary)
    {
        Name = name;

        if (salary >= 0)
        {
            this.salary = salary;
        }
    }

    public void IncreaseSalary(double amount)
    {
        if (amount > 0)
        {
            salary += amount;
        }
    }
}

External code:

Employee employee = new Employee("Hariom", 50000);

Console.WriteLine(employee.Name);
Console.WriteLine(employee.Salary);

employee.IncreaseSalary(5000);

External code cannot directly do:

employee.salary = -999999;

That's the point.

37. The Most Important Mental Model

When designing a class, ask:

1. What data does the object own?
          ↓
2. What data should outsiders see?
          ↓
3. What data should outsiders modify?
          ↓
4. What rules must always remain true?
          ↓
5. What operations should control changes?

Then choose access modifiers.

Example:

balance
→ private

Balance
→ public get

Deposit()
→ public

Withdraw()
→ public

ValidateSomething()
→ private
38. Access Modifier Decision Guide

When writing a member, ask:

Should everyone be able to use it?
public
Should only this class use it?
private
Should derived classes also use it?
protected
Should code in the same assembly use it?
internal
Same assembly OR derived classes?
protected internal
Same assembly AND derived classes?
private protected
39. Interview-Level Comparison
Modifier	Same Class	Derived Class	Same Assembly	Other Assembly
private	✅	❌	❌*	❌
protected	✅	✅	❌ unless derived	❌ unless derived
internal	✅	✅	✅	❌
protected internal	✅	✅	✅	✅ if derived
private protected	✅	✅ within same assembly	✅*	❌
public	✅	✅	✅	✅

* Access within the containing type is always permitted; the table is simplified for learning.

40. One Critical Rule

Do not choose public just because it makes your code easier to access.

Bad approach:

class BankAccount
{
    public double balance;
    public string password;
    public bool isValid;
}

Better approach:

class BankAccount
{
    private double balance;
    private string password;
    private bool isValid;
}

Then expose only the necessary interface.

This is the mindset of good OOP design.

41. Complete Example
class BankAccount
{
    private double balance;

    public string AccountNumber { get; private set; }

    public double Balance
    {
        get
        {
            return balance;
        }
    }

    public BankAccount(string accountNumber)
    {
        AccountNumber = accountNumber;
        balance = 0;
    }

    public void Deposit(double amount)
    {
        if (amount <= 0)
        {
            return;
        }

        balance += amount;
    }

    public bool Withdraw(double amount)
    {
        if (amount <= 0 || amount > balance)
        {
            return false;
        }

        balance -= amount;
        return true;
    }
}

Usage:

BankAccount account = new BankAccount("ACC101");

account.Deposit(10000);

Console.WriteLine(account.Balance);

bool success = account.Withdraw(3000);

Console.WriteLine(account.Balance);

The design is:

BankAccount
│
├── private balance
│
├── public AccountNumber
│      └── private set
│
├── public Balance
│      └── get only
│
├── public Deposit()
│
└── public Withdraw()

This is a strong example of encapsulation.

42. Common Mistakes
Mistake 1

Thinking:

private = inaccessible everywhere

Wrong.

It is accessible inside its containing type.

Mistake 2

Thinking:

protected = public for derived classes

Not exactly.

protected is specifically available to the containing type and derived types, subject to C#'s access rules.

Mistake 3

Thinking:

internal = private

No.

internal allows access throughout the same assembly.

Mistake 4

Thinking:

encapsulation = private keyword

No.

private helps implement encapsulation.

Encapsulation is the broader design principle.

Mistake 5

Making everything public:

public field;
public helperMethod();
public internalState;

This exposes implementation details unnecessarily.
